# CLAUDE.md — Сайт поздравительных открыток

Этот файл — постоянный контекст проекта для Claude Code. Сверяйся с ним при каждой задаче.
Полное SEO ТЗ лежит в `docs/seo-requirements.md` и является источником истины при любых противоречиях.
Процесс мультиагентской разработки, состав агентов и обязательный протокол завершения задачи — в `agent_readme.md`.
Готовые промпты запуска агентов, матрица параллельности и чек-лист приёмки их работы — в `docs/agents-launch.md`.

## О проекте

Сайт с поздравительными открытками (изображения генерируются нейросетями, публикуются только после ручной модерации). География: Россия и СНГ. Поисковые системы: Яндекс и Google. Монетизация: медийная и контекстная реклама. Органический трафик из поиска — главный канал, поэтому **SEO-требования имеют приоритет над скоростью разработки и удобством кода**.

## Стек

| Слой | Технология | Роль |
|---|---|---|
| Фронтенд | Astro (гибридный режим) | Статика для стабильных страниц, SSR для каталога |
| Админка и API | Payload CMS | Коллекции, черновики, SEO-поля, история изменений |
| База данных | PostgreSQL | Единственное хранилище данных |
| Изображения | sharp + S3-совместимое хранилище | AVIF/WebP, srcset, pHash-дедупликация |
| Тесты | Vitest + Playwright | Юнит- и SEO-приёмочные тесты |
| Язык | TypeScript строго везде | Один язык на весь монорепозиторий |

## Модель данных (Payload-коллекции)

- `cards` — карточка открытки. Один canonical URL навсегда. Связь many-to-many с `collections` (открытка входит в несколько подборок без дублирования URL). Поля: изображение, title, h1, alt, подпись, описание, повод, адресат, стиль, настроение, форматы/размеры, условия использования, pHash.
- `collections` — подборки и посадочные (праздничные, по адресату, по стилю). Иерархия соответствует структуре URL. Поля: title, h1, description, вводный текст, canonical, robots-директива, дата содержательного обновления, ответственный редактор.
- `redirects` — 301-редиректы, редактируются в админке, применяются в middleware Astro.
- `seo-history` — история изменений SEO-полей (заполняется хуками автоматически, включая автора изменения: человек или сервисный аккаунт).

Статусная модель контента: `draft` → `review` → `published`.
- `draft` — рабочий черновик, `noindex`, вне sitemap.
- `review` — готово к проверке человеком: контент, метатеги и перелинковка заполнены, дубли проверены. По-прежнему `noindex`, вне sitemap.
- `published` — опубликовано человеком; только здесь возможен `index,follow` (при выполнении условий п. 5.1 ТЗ).

Правила модели:
- Новая запись создаётся ТОЛЬКО в статусе `draft` с `noindex`. Перевод в `published` и открытие в `index,follow` — осознанное действие человека, никогда не автоматическое (требование п. 7.1 и п. 23 ТЗ).
- Хук `beforeChange`: URL (slug) после первой публикации становится неизменяемым. Смена URL возможна только с одновременным созданием 301-редиректа.
- Хук проверки метатегов: при сохранении ищет совпадения title/description по каталогу и показывает предупреждение.
- Воркер pHash: при загрузке изображения считает перцептивный хеш и показывает редактору визуально похожие уже опубликованные открытки.

## Внешнее управление (AI-редактор через API)

Payload автоматически отдаёт REST и GraphQL API для всех коллекций — отдельный API-слой не пишется. Все защитные правила реализуются в хуках Payload на сервере, поэтому действуют одинаково для админки и для API: обойти их через внешний клиент невозможно.

Роли и права (access control в конфигах коллекций):
- `admin` (человек) — полные права, включая публикацию, `index,follow`, редиректы, изменение URL.
- `ai-editor` (сервисный аккаунт, API-ключ) — может: создавать и редактировать записи в `draft`, загружать изображения, заполнять метаданные и alt, привязывать карточки к подборкам, расставлять внутренние ссылки, переводить `draft` → `review`. НЕ может: переводить в `published`, менять `index/noindex`, изменять slug после первой публикации, создавать/менять редиректы, трогать robots-директивы и sitemap.
- Граница автоматизации фиксирована ТЗ: агент доводит контент до `review`, решение о публикации и открытии в индекс принимает человек.

Аудит: `seo-history` фиксирует автора каждого изменения (пользователь или сервисный аккаунт) — любой шаг агента прослеживаем.

Интеграция агента: тонкая обёртка над Payload API (при использовании Claude — MCP-сервер) с операциями уровня задач: «создай черновик карточки», «прикрепи к подборкам», «проверь дубли», «переведи в review». Бизнес-правила при этом остаются в хуках Payload, обёртка их не дублирует.

## Правила URL — нарушать запрещено

- Нижний регистр, транслитерация, дефисы между словами. Без кириллицы, пробелов, подчёркиваний, параметров.
- Единое правило завершающего слеша по всему сайту (выбрано: со слешем).
- URL не зависит от ID, даты публикации, позиции в меню. Смена заголовка НЕ меняет URL.
- Год не добавляется в URL ежегодных праздников.
- Один материал доступен только по одному пути. Карточка: `/otkrytki/<slug>/`.
- Изменение существующего URL без одиночного 301 — критическая ошибка. Цепочки редиректов запрещены.

## Правила индексации

- В `index,follow` страница попадает только при выполнении условий п. 5.1 ТЗ: подтверждённый спрос, отдельный интент, достаточно открыток (ориентир 20–40 для широкой темы), уникальные title/H1/вводный текст, включена в навигацию, есть self-canonical, отвечает 200.
- Всегда `noindex` + вне sitemap: внутренний поиск, фильтры/сортировка, страницы генерации и превью, личный кабинет, черновики, служебные страницы, автоматические теги, пагинация.
- Пустая или слабая страница не отдаёт 200 как полноценная посадочная.

## Рендеринг — архитектурные инварианты

- title, H1, canonical, хлебные крошки, основной текст, ссылки и первые изображения присутствуют в HTML-ответе сервера. Проверка: страница полноценна при отключённом JS.
- Навигация — только `<a href>`. Hash-маршрутизация запрещена.
- Клиентский JS в Astro — только точечные острова (кнопка скачивания, фильтры). Фильтры меняют представление, но не создают индексируемых URL.
- Бесконечная лента запрещена; только обычная пагинация с постоянными URL.

## Изображения

- Вывод через `<img>`/`<picture>` с реальным `src`, обязательные `width` и `height`, `srcset`/`sizes`.
- Первое крупное изображение: без lazy loading, допустим `fetchpriority="high"`. Остальные: `loading="lazy"`.
- Форматы: AVIF и WebP + резервный JPEG. Оригиналы хранятся отдельно от оптимизированных копий.
- Имя файла — короткое описательное на транслите: `otkrytka-mame-na-8-marta-s-tulpanami.webp`. URL файла постоянный.
- `alt` — естественное описание, не перечень ключей. Декоративные элементы — пустой `alt`.

## Sitemap и robots

- Sitemap-индекс: `/sitemap.xml` → sections, cards (по 50 000 URL max), images (image sitemap).
- Включаются только абсолютные канонические URL со статусом 200 и разрешением на индексацию. Редиректы, 404, noindex, параметры — исключаются. Это проверяется тестом, а не соглашением.
- `lastmod` меняется только при содержательном обновлении.
- Sitemap перегенерируется хуками Payload при публикации/переносе/удалении.
- robots.txt: закрыты `/search/`, `/account/`, `/admin/`, `/generator/preview/`; CSS/JS/изображения не блокируются; указана абсолютная ссылка на sitemap-индекс.

## HTTP-статусы

| Ситуация | Ответ |
|---|---|
| Опубликованная страница | 200 |
| Перенос | одиночный 301 |
| Удалено без замены | 404/410 |
| Удалено с заменой | 301 на релевантный URL |
| Сервис недоступен | 503 + Retry-After |

Массовый редирект удалённых страниц на главную запрещён. Страница 404 отдаёт настоящий 404 и содержит навигацию.

## Производительность (75-й перцентиль, мобильные)

LCP ≤ 2,5 с · INP < 200 мс · CLS < 0,1 · TTFB ≤ 0,8 с · HTML без изображений ≤ 150 КБ.

Brotli, HTTP/2+, длительное кеширование статики, критический CSS первым, некритический JS — отложенно, размеры изображений и рекламных контейнеров резервируются заранее (реклама не должна давать сдвиг макета).

## Структурированные данные (JSON-LD)

Главная: `WebSite` + `Organization`. Подборка: `CollectionPage` + `ItemList` + `BreadcrumbList`. Карточка: `WebPage` + `ImageObject` (contentUrl, name, description, creator, creditText, copyrightNotice, license, acquireLicensePage) + `BreadcrumbList`. Разметка соответствует видимому содержимому. Фиктивные отзывы, рейтинги и авторы запрещены.

## SEO-тесты (tests/seo/) — контур обратной связи

Playwright-тесты кодируют чек-лист приёмки из п. 22 ТЗ и гоняются на тестовой выборке: главная, раздел, праздничная посадочная, дочерняя подборка, карточка, пагинация, внутренний поиск, URL с параметрами, удалённая карточка, 404.

Обязательные проверки:
- уникальные title/H1/description на выборке, ровно один H1;
- абсолютный self-canonical на всех индексируемых страницах;
- контент и первые изображения присутствуют в HTML без выполнения JS;
- внутренние ссылки — `<a href>`;
- 404 отдаёт 404; удалённая карточка не отдаёт 200;
- sitemap: только 200 + canonical + indexable, валидный XML, image sitemap валиден;
- у `<img>` есть src, width, height, alt; первый экран без lazy на главном изображении;
- фильтры и поиск не создают индексируемых дублей;
- нет страниц-сирот (каждая индексируемая страница достижима за ≤ 4 перехода от главной).

**Если меняешь шаблон страницы, роутинг, sitemap или коллекции — запусти `pnpm test:seo` до и после.**

## Критические запреты (из п. 23 ТЗ)

- НЕ создавать URL массово до готовности контента.
- НЕ публиковать результат генерации автоматически без ручной проверки.
- НЕ индексировать поиск, фильтры, теги, пустые страницы.
- НЕ генерировать шаблонные SEO-тексты с заменой пары слов.
- НЕ скрывать контент за JavaScript.
- НЕ менять существующие URL без 301.
- НЕ добавлять в sitemap неканонические/закрытые страницы.
- НЕ создавать региональные копии (`/ru/`, `/kz/`, `/by/`) без уникального содержания.
- НЕ использовать отдельный мобильный поддомен.

## Соглашения по коду

- TypeScript strict, без `any`. Типы Payload генерируются из коллекций (`pnpm generate:types`) — используй их, не дублируй вручную.
- Payload и Astro развиваются быстро: при работе с их API сверяйся с типами и исходниками в `node_modules`, а не пиши по памяти.
- Логика SEO (canonical, robots, sitemap, редиректы) живёт в коде и покрыта тестами — никаких «настроим потом в админке».
- Коммиты небольшие, каждый оставляет проект в состоянии, где `pnpm verify` зелёный.

## О проекте

Сайт с поздравительными открытками (изображения генерируются нейросетями, публикуются только после ручной модерации). География: Россия и СНГ. Поисковые системы: Яндекс и Google. Монетизация: медийная и контекстная реклама. Органический трафик из поиска — главный канал, поэтому **SEO-требования имеют приоритет над скоростью разработки и удобством кода**.

## Модель данных (Payload-коллекции)

- `cards` — карточка открытки. Один canonical URL навсегда. Связь many-to-many с `collections` (открытка входит в несколько подборок без дублирования URL). Поля: изображение, title, h1, alt, подпись, описание, повод, адресат, стиль, настроение, форматы/размеры, условия использования, pHash.
- `collections` — подборки и посадочные (праздничные, по адресату, по стилю). Иерархия соответствует структуре URL. Поля: title, h1, description, вводный текст, canonical, robots-директива, дата содержательного обновления, ответственный редактор.
- `redirects` — 301-редиректы, редактируются в админке, применяются в middleware Astro.
- `seo-history` — история изменений SEO-полей (заполняется хуками автоматически, включая автора изменения: человек или сервисный аккаунт).

Статусная модель контента: `draft` → `review` → `published`.
- `draft` — рабочий черновик, `noindex`, вне sitemap.
- `review` — готово к проверке человеком: контент, метатеги и перелинковка заполнены, дубли проверены. По-прежнему `noindex`, вне sitemap.
- `published` — опубликовано человеком; только здесь возможен `index,follow` (при выполнении условий п. 5.1 ТЗ).

Правила модели:
- Новая запись создаётся ТОЛЬКО в статусе `draft` с `noindex`. Перевод в `published` и открытие в `index,follow` — решение человека с ролью `admin`; автоматическим, то есть исходящим от кода, хука, воркера или сервисного аккаунта, оно не бывает никогда (п. 7.1 и п. 23 ТЗ).
- Применить это решение `admin` может как поштучно, так и **пакетно — к выбранной им выборке записей одной операцией**, когда уверен в результате (решение Ч-07, 2026-08-21; ослабляет прежнее требование «всегда поштучно»). Граница автоматизации при этом не сдвигается: пакетная операция доступна только роли `admin` из админки, `ai-editor` ни публиковать, ни менять `index/noindex` не может ни поштучно, ни пакетно. Массовая публикация без выбора человеком (по расписанию, по фильтру из кода, по вызову API сервисным аккаунтом) остаётся запрещённой.
- Хук `beforeChange`: URL (slug) после первой публикации становится неизменяемым. Смена URL возможна только с одновременным созданием 301-редиректа.
- Хук проверки метатегов: при сохранении ищет совпадения title/description по каталогу и показывает предупреждение.
- Воркер pHash: при загрузке изображения считает перцептивный хеш и показывает редактору визуально похожие уже опубликованные открытки.

## Внешнее управление (AI-редактор через API)

Payload автоматически отдаёт REST и GraphQL API для всех коллекций — отдельный API-слой не пишется. Все защитные правила реализуются в хуках Payload на сервере, поэтому действуют одинаково для админки и для API: обойти их через внешний клиент невозможно.

Роли и права (access control в конфигах коллекций):
- `admin` (человек) — полные права, включая публикацию, `index,follow`, редиректы, изменение URL.
- `ai-editor` (сервисный аккаунт, API-ключ) — может: создавать и редактировать записи в `draft`, загружать изображения, заполнять метаданные и alt, привязывать карточки к подборкам, расставлять внутренние ссылки, переводить `draft` → `review`. НЕ может: переводить в `published`, менять `index/noindex`, изменять slug после первой публикации, создавать/менять редиректы, трогать robots-директивы и sitemap.
- Граница автоматизации фиксирована ТЗ: агент доводит контент до `review`, решение о публикации и открытии в индекс принимает человек.

Аудит: `seo-history` фиксирует автора каждого изменения (пользователь или сервисный аккаунт) — любой шаг агента прослеживаем.

Интеграция агента: тонкая обёртка над Payload API (при использовании Claude — MCP-сервер) с операциями уровня задач: «создай черновик карточки», «прикрепи к подборкам», «проверь дубли», «переведи в review». Бизнес-правила при этом остаются в хуках Payload, обёртка их не дублирует.

## Правила URL — нарушать запрещено

- Нижний регистр, транслитерация, дефисы между словами. Без кириллицы, пробелов, подчёркиваний, параметров.
- Единое правило завершающего слеша по всему сайту: **БЕЗ завершающего слеша** (решение Ч-21, 2026-08-21; заменяет прежний выбор «со слешем»). Канонический вид маршрута страницы — `/otkrytki/8-marta`; обращение с завершающим слешем отдаёт одиночный 301 на форму без слеша. Область применения — маршруты страниц; предикат `isPageRoute()` в `packages/shared` отделяет их от URL файлов (URL файлов слешем не заканчиваются и middleware их не нормализует), а маршруты админки Payload отдаёт `apps/cms` вне нормализации Astro.
- URL не зависит от ID, даты публикации, позиции в меню. Смена заголовка НЕ меняет URL.
- Год не добавляется в URL ежегодных праздников.
- Один материал доступен только по одному пути. Карточка: `/otkrytki/<slug>`.
- Изменение существующего URL без одиночного 301 — критическая ошибка. Цепочки редиректов запрещены.
- Пагинация — сегментом пути `/page/N`, не query-параметром (решение Ч-05). Первая страница любого списка — каталога или подборки — живёт по базовому URL; `/page/1` не существует ни на одном уровне.
- Таксономия — с группирующими узлами в контейнере `/podborki` (решение Ч-04-5, уточнено человеком 2026-08-22). Ветвь праздников — `/podborki/prazdniki/<tema>`, пара «праздник × адресат» — `/podborki/prazdniki/<tema>/<adresat>`, адресаты без праздника — `/podborki/adresaty/<adresat>`. Порядок сегментов только «повод → уточнение»; обратный порядок не создаётся никогда (решение Ч-04-7).
- Пространства имён подборок и карточек РАЗВЕДЕНЫ: подборки под `/podborki`, карточки под `/otkrytki/<slug>` (уточнение человека 2026-08-22, отменяет прежнюю запись «Ч-04-9», по которой подборки жили в `/otkrytki`). Следствие, ради которого выбран этот вариант: коллизия «карточка со slug `prazdniki` против группирующего узла» невозможна структурно, а не удерживается проверкой. Проверка уникальности итогового пути внутри каждой коллекции при этом остаётся обязательной (Э1-05 — сборка пути подборки из цепочки родителей, Э1-09 — уникальность и неизменяемость slug), потому что две подборки с разными родителями могут дать один итоговый путь.
- Slug праздников (решение Ч-04-4): праздник с фиксированной датой — `<число>-<месяц>` (`8-marta`, `9-maya`, `14-fevralya`, `23-fevralya`); без фиксированной даты или известный только названием — короткое название (`paskha`, `novyy-god`, `den-materi`). Длинные официальные названия не используются.
- Максимальная длина slug — 80 символов, имени файла — 68; превышение отклоняется, а не усекается (решение Ч-26). Slug из одних цифр отклоняется (решение Ч-27).
- Из-за группирующих узлов путь до карточки в паре «праздник × адресат» получает 5 сегментов. Требование «≤ 4 перехода от главной» держится на прямых ссылках из меню и с главной на праздничные узлы — это требование к шаблону, а не оформление (следствие Ч-04-5). Достижимость карточек за первой страницей списка обеспечивают обязательные блоки перелинковки на карточке, отрендеренные сервером (решение Ч-04-8).
- Абсолютный URL (canonical, sitemap, robots, JSON-LD) собирается ТОЛЬКО из env-параметра `SITE_URL` через единственный хелпер в `packages/shared`. Хост не хардкодится в продуктовом коде: ни дефолта, ни фолбэка (синтетическое значение хоста в фикстуре юнит-теста допустимо и нужно — им проверяется сама сборка URL). Значение на время разработки — `http://otkritka.test` (решение Ч-02, 2026-08-21), задаётся в `.env`; в `.env.example` `SITE_URL` остаётся пустым, и пустое значение обязано валить сборку с внятной ошибкой. Значения по умолчанию в коде (включая `localhost` и тестовый домен) запрещены. Подставлять плейсхолдер вместо ошибки нельзя — иначе canonical и sitemap молча соберутся не на том хосте.
- Контракт `SITE_URL`: схема + хост без завершающего слеша, ровно один хост на весь сайт. Нормализация хвостового слеша у значения — обязанность хелпера, а не автора `.env`; покрывается unit-тестом.
- Зарезервированные маршруты. Проверка выполняется по ИТОГОВОМУ пути записи, а не по «уровню» slug, и состоит ровно из трёх правил:
  1. сегмент `page` запрещён на любой позиции (иначе запись сталкивается с пагинацией `/page/N`);
  2. каждый маршрут реестра помечен одним из двух видов, и вид определяет проверку (плоский список строк без пометки — ошибка реализации):
     - **занят целиком** (`/search`, `/account`, путь админки, `/generator/preview`, `/o-proekte`, `/usloviya`, `/kontakty`, `/robots.txt`, `/sitemap.xml`): запрещено и совпадение, и любой путь под ним — `/search/istoriya` отклоняется;
     - **контейнер** (`/`, `/otkrytki`, `/podborki`): совпадение запрещено (собственная запись с таким путём), пути под ним — норма, это и есть место для записей. Группирующие узлы таксономии (`/podborki/prazdniki`, `/podborki/adresaty`) в реестр НЕ попадают: это данные, а не маршруты, и защищает их проверка уникальности итогового пути в хуках Payload;

  Для файловых маршрутов (`/robots.txt`, `/sitemap.xml` и производные) резервируется имя БЕЗ расширения: заняты и `/sitemap.xml`, и `/sitemap`.
  3. корневые сегменты реестра резервируются дополнительно по имени сегмента на первом уровне: slug `sitemap` даёт `/sitemap`, который формально не совпадает ни с чем, но путается с `/sitemap.xml`.
  Единственный машинный источник — реестр в `packages/shared`; реестр хранит только пути (маршруты страниц — в канонической форме БЕЗ завершающего слеша, решение Ч-21); форма директив `Disallow` из реестра не выводится и задана решением Ч-22 (см. «Sitemap и robots»). Стартовое наполнение реестра (переносится в код один раз, дальше правится только там; остальные документы ссылаются, а не копируют) — контейнеры: `/`, `/otkrytki`, `/podborki`; занятые целиком: `/search`, `/account`, `/o-proekte`, `/usloviya`, `/kontakty`, `/generator/preview`, `/pozdravleniya` (зарезервирован под этап 2 развития — резерв в реестре не разрешает создавать страницу, запрет по Ч-20 остаётся), `/robots.txt`, `/sitemap.xml` и производные sitemap, плюс путь админки — **вычисляемый из `PAYLOAD_ADMIN_PATH`, а не записанный строкой**: при нестандартном значении сегмент админки обязан попасть в резерв, иначе подборка с таким slug займёт тот же путь. Покрыто негативным тестом, включая случай нестандартного `PAYLOAD_ADMIN_PATH`.

## Правила индексации

- В `index,follow` страница попадает только при выполнении условий п. 5.1 ТЗ: подтверждённый спрос, отдельный интент, достаточно открыток (ориентир 20–40 для широкой темы), уникальные title/H1/вводный текст, включена в навигацию, есть self-canonical, отвечает 200.
- Всегда `noindex` + вне sitemap: внутренний поиск, фильтры/сортировка, страницы генерации и превью, личный кабинет, черновики, технические служебные страницы, автоматические теги, пагинация. Информационные страницы `/o-proekte`, `/usloviya`, `/kontakty` — именованное исключение (решение Ч-23), см. «Sitemap и robots».
- Стили и настроения — неиндексируемый фильтр, отдельных URL под них не создаётся (решение Ч-04-3). Порог перекрытия выдачи, при котором две темы не разводятся по разным URL, — 80 % (решение Ч-04-6).
- Условие «подтверждённый спрос» п. 5.1 данными пока не подтверждено: частотности нет, приоритет наполнения строится по календарю праздников как допущение (решение Ч-04-1). Решение об `index,follow` принимает человек, ссылаться на «подтверждённый спрос» как на выполненное условие нельзя.
- Пагинация (`/page/N`, страницы 2+): директива `noindex,follow` — ссылки обходятся, страницы в индекс не идут и в sitemap не попадают (решение Ч-01b/Ч-05, снимает расхождение с §5.3 продуктового ТЗ).
- Пустая или слабая страница не отдаёт 200 как полноценная посадочная.

## Рендеринг — архитектурные инварианты

- title, H1, canonical, хлебные крошки, основной текст, ссылки и первые изображения присутствуют в HTML-ответе сервера. Проверка: страница полноценна при отключённом JS.
- Навигация — только `<a href>`. Hash-маршрутизация запрещена.
- Клиентский JS в Astro — только точечные острова (кнопка скачивания, фильтры). Фильтры меняют представление, но не создают индексируемых URL.
- Бесконечная лента запрещена; только обычная пагинация с постоянными URL.

## Изображения

- Вывод через `<img>`/`<picture>` с реальным `src`, обязательные `width` и `height`, `srcset`/`sizes`.
- Первое крупное изображение: без lazy loading, допустим `fetchpriority="high"`. Остальные: `loading="lazy"`.
- Форматы: AVIF и WebP + резервный JPEG с расширением `.jpg` (решение Ч-30). Оригиналы хранятся отдельно от оптимизированных копий.
- Имя файла — короткое описательное на транслите: `otkrytka-mame-na-8-marta-s-tyulpanami.webp` (образец приведён в соответствие с таблицей транслитерации, правило `ю → yu` — решение Ч-24). URL файла постоянный.
- `alt` — естественное описание, не перечень ключей. Декоративные элементы — пустой `alt`.
- Набор ширин `srcset` — 320/640/960/1280/1920, **окончательный**: добавление ширин запрещено, потому что новая ширина отменяет fallback в натуральную ширину и делает уже выданный ключ невоспроизводимым (решение Ч-09). Минимальная ширина исходника при загрузке — 640 px, уже — отказ на загрузке. Апскейл не делается: ширина больше исходной пропускается.
- Сегмент `revision` в ключе производной — короткий хеш байтов оригинала (решение Ч-28). Меняется только при замене байтов изображения; выводить его из `updatedAt`, версии записи или счётчика сохранений запрещено — иначе каждое сохранение переписывает URL всех производных.
- Совпадение имени и ревизии у двух изображений разводится суффиксом `-N` (решение блока 5 п. 3, 2026-08-21). Суффикс присваивается один раз при загрузке и **хранится в записи**: при перегенерации берётся из записи, не пересчитывается, после удаления не переиспользуется — иначе путь зависел бы от состояния хранилища.
- Порог pHash-похожести — 14 (решение Ч-08), параметр `PHASH_DISTANCE_THRESHOLD`. Это подсказка редактору, а не автоблокировка. Повёрнутый дубль DCT-pHash не находит ни при каком пороге — ограничение алгоритма, не настройка.
- Качество кодирования — avif 50 / webp 80 / jpeg 82, `progressive: true` у JPEG (решение Ч-29); все значения настраиваемые, пересматриваются после замера на реальных открытках.
- Хранилище до переезда на S3 — локальная ФС за адаптером (решение Ч-03, 2026-08-21): оригиналы вне публичного корня, производные отдаются с собственного домена по пути `/media/...` с `Cache-Control: public, max-age=31536000, immutable`. Отдельного `IMAGES_CDN_ORIGIN` нет — абсолютные URL изображений собирает тот же хелпер из `SITE_URL`, именованного исключения из правила не требуется. При переезде на S3 путь сохраняется, меняется только origin отдачи.

## Sitemap и robots

- Sitemap-индекс: `/sitemap.xml` → sections, cards (по 50 000 URL max), images (image sitemap).
- Включаются только абсолютные канонические URL со статусом 200 и разрешением на индексацию. Редиректы, 404, noindex, параметры — исключаются. Это проверяется тестом, а не соглашением.
- `lastmod` меняется только при содержательном обновлении.
- Sitemap перегенерируется хуками Payload при публикации/переносе/удалении.
- robots.txt (форма директив — решение Ч-22, 2026-08-21): `Disallow` пишется **без завершающего слеша** — `Disallow: /search`, `Disallow: /account`, `Disallow: /generator/preview`. Форма префиксная, поэтому покрывает и `/search`, и `/search/`, тогда как форма со слешем не покрыла бы голый `/search`, который краулер запрашивает первым. CSS/JS/изображения не блокируются; указана абсолютная ссылка на sitemap-индекс.
- Путь админки в `robots.txt` **не публикуется** (решение Ч-22): публикация только подсказывает адрес админки. Админка закрывается заголовком `X-Robots-Tag: noindex` и авторизацией; `PAYLOAD_ADMIN_PATH` в robots не подставляется. В реестре зарезервированных маршрутов путь админки при этом остаётся — он вычисляется из `PAYLOAD_ADMIN_PATH`, а не пишется строкой.
- Информационные страницы `/o-proekte`, `/usloviya`, `/kontakty` — статические маршруты Astro, а не записи CMS. Именованное исключение (решение Ч-23, 2026-08-21): они получают `index,follow`, self-canonical и входят в sitemap — **при условии, что наполнены реальным текстом**; пока стоят заглушки, остаются `noindex` и вне sitemap. Ссылка из `acquireLicensePage` доводом за индексацию не является: она работает и на неиндексируемой странице.

## HTTP-статусы

| Ситуация | Ответ |
|---|---|
| Опубликованная страница | 200 |
| Перенос | одиночный 301 |
| Удалено без замены | 404/410 |
| Удалено с заменой | 301 на релевантный URL |
| Сервис недоступен | 503 + Retry-After |

Массовый редирект удалённых страниц на главную запрещён. Страница 404 отдаёт настоящий 404 и содержит навигацию.

## Производительность (75-й перцентиль, мобильные)

LCP ≤ 2,5 с · INP < 200 мс · CLS < 0,1 · TTFB ≤ 0,8 с · HTML без изображений ≤ 150 КБ.

Brotli, HTTP/2+, длительное кеширование статики, критический CSS первым, некритический JS — отложенно, размеры изображений и рекламных контейнеров резервируются заранее (реклама не должна давать сдвиг макета).

## Структурированные данные (JSON-LD)

Главная: `WebSite` + `Organization`. Подборка: `CollectionPage` + `ItemList` + `BreadcrumbList`. Карточка: `WebPage` + `ImageObject` (contentUrl, name, description, creator, creditText, copyrightNotice, license, acquireLicensePage) + `BreadcrumbList`. Разметка соответствует видимому содержимому. Фиктивные отзывы, рейтинги и авторы запрещены.

## SEO-тесты (tests/seo/) — контур обратной связи

Playwright-тесты кодируют чек-лист приёмки из п. 22 ТЗ и гоняются на тестовой выборке: главная, раздел, праздничная посадочная, дочерняя подборка, карточка, пагинация, внутренний поиск, URL с параметрами, удалённая карточка, 404.

На окружении, где гоняется приёмка, `SITE_URL` и `BASE_URL` указывают на один и тот же хост — иначе self-canonical укажет на другой хост и проверка canonical либо ложно упадёт, либо будет ослаблена. Ослаблять её запрещено; расхождение хостов — это ошибка конфигурации окружения, а не теста.

Обязательные проверки:
- уникальные title/H1/description на выборке, ровно один H1;
- абсолютный self-canonical на всех индексируемых страницах;
- контент и первые изображения присутствуют в HTML без выполнения JS;
- внутренние ссылки — `<a href>`;
- 404 отдаёт 404; удалённая карточка не отдаёт 200;
- sitemap: только 200 + canonical + indexable, валидный XML, image sitemap валиден;
- у `<img>` есть src, width, height, alt; первый экран без lazy на главном изображении;
- фильтры и поиск не создают индексируемых дублей;
- нет страниц-сирот (каждая индексируемая страница достижима за ≤ 4 перехода от главной).

**Если меняешь шаблон страницы, роутинг, sitemap или коллекции — запусти `pnpm test:seo` до и после.**

## Критические запреты (из п. 23 ТЗ)

- НЕ создавать URL массово до готовности контента.
- НЕ публиковать результат генерации автоматически без решения человека. Пакетная публикация выборки, выбранной администратором вручную, разрешена (Ч-07) — автоматической считается публикация, инициированная кодом, расписанием, хуком или сервисным аккаунтом.
- НЕ индексировать поиск, фильтры, теги, пустые страницы.
- НЕ генерировать шаблонные SEO-тексты с заменой пары слов.
- НЕ скрывать контент за JavaScript.
- НЕ менять существующие URL без 301.
- НЕ добавлять в sitemap неканонические/закрытые страницы.
- НЕ создавать региональные копии (`/ru/`, `/kz/`, `/by/`) без уникального содержания.
- НЕ использовать отдельный мобильный поддомен.

## Соглашения по коду

- TypeScript strict, без `any`. Типы Payload генерируются из коллекций (`pnpm generate:types`) — используй их, не дублируй вручную.

- Логика SEO (canonical, robots, sitemap, редиректы) живёт в коде и покрыта тестами — никаких «настроим потом в админке».
- Коммиты небольшие, каждый оставляет проект в состоянии, где `pnpm verify` зелёный.

# apps/cms — Payload CMS

Владелец: агент `payload-cms`.

Payload 3.88.0 на PostgreSQL, админка и API живут внутри Next.js 16 — так
устроен Payload 3: отдельного сервера у него нет, админка и REST/GraphQL
подключаются к приложению Next через маршруты в `src/app/(payload)/`.

Отдельный API-слой не пишется: Payload сам отдаёт REST и GraphQL. Поэтому все
защитные правила живут в серверных хуках и access control — так они действуют
одинаково для админки и для внешнего AI-редактора, и обойти их через API нельзя.

## Команды

```bash
pnpm --filter @otkritka/cms run ensure-db            # создать базу из DATABASE_URL, если её нет
pnpm dev                                             # из корня: поднимает CMS на http://localhost:3010
pnpm generate:types                                  # из корня: src/payload-types.ts из коллекций
pnpm --filter @otkritka/cms run generate:importmap    # после добавления кастомных компонентов админки
pnpm --filter @otkritka/cms run build                 # production-сборка Next
pnpm --filter @otkritka/cms run check                 # tsc --noEmit (входит в корневой pnpm check)
```

Порт 3010, а не 3000: на машине разработки 3000 уже занят другим процессом.

## Путь админки и `PAYLOAD_ADMIN_PATH`

Payload 3 привязывает админку к **физическому** каталогу
`src/app/(payload)/admin/[[...segments]]`, а `routes.admin` в конфиге влияет
только на генерацию ссылок. Каталог из переменной окружения не переименовать,
поэтому связка сделана в `next.config.mjs`:

- запрос на настроенный путь переписывается (`rewrite`) на физический `/admin`;
- физический `/admin` отдаёт 307 на настроенный путь, чтобы у одной админки не
  было двух живых адресов.

Значения по умолчанию у `PAYLOAD_ADMIN_PATH` нет намеренно — так же, как в
реестре зарезервированных маршрутов в `packages/shared`. Дефолт в одном из двух
мест означал бы, что админка обслуживает один путь, а зарезервирован другой.

Все ответы приложения помечены `X-Robots-Tag: noindex, nofollow`: по решению
Ч-22 путь админки в `robots.txt` не публикуется, закрытие делается заголовком и
авторизацией.

## Что реализовано

Этапы 1 и 2 закрыты полностью. Ниже — не список задач, а состав защиты: что
именно нельзя сделать через API и где это записано.

| Возможность | Где реализовано |
|---|---|
| Коллекции `cards`, `collections`, `card-images`, `redirects`, `seo-history`, `image-name-claims`, `users` | `src/collections/` |
| Матрица прав `admin` / `ai-editor` (Ч-16), API-ключи с ролью владельца | `src/access/policies.ts`, `src/collections/users.ts` |
| Статусная модель `draft` → `review` → `published` с валидацией полноты перед `review` | `src/collections/status-model.ts` |
| Публикация и `index,follow` — только человек, только отдельными действиями | там же |
| Пакетная операция по ЯВНО выбранным записям (Ч-07), запрет ЛЮБОЙ смены статуса по фильтру и запрет одного решения о судьбе URL на выборку | там же (`assertBulkChangeAllowed`) |
| Год не попадает в ИТОГОВЫЙ адрес карточки и любого узла подборок (условие C3) | `@otkritka/shared` (`findYearInSlug`) + `content-hooks.ts`, `collection-path.ts` |
| Роль пользователя задаётся явно: значения по умолчанию у неё нет | `users.ts` (`resolveCreateRole`) |
| Неизменяемость URL после первой публикации, смена URL одной операцией с одиночным 301, схлопывание цепочек, запрет петель | `src/collections/content-hooks.ts`, `redirects-plan.ts`, `redirect-sync.ts` |
| Решение о судьбе URL при снятии с публикации (301 / 404 / 410) | `status-model.ts` + `content-hooks.ts` |
| Иерархия подборок: путь в записи с уникальным индексом БД, матрица допустимых родителей, перенос поддерева с 301 на каждый путь | `collections.ts`, `collection-path.ts` |
| `seo-history` с автором каждого изменения (человек или сервисный аккаунт), только чтение | `seo-history.ts`, `seo-history-diff.ts` |
| Загрузка изображений: производные AVIF/WebP/JPEG, pHash, постоянные пути файлов, суффикс `-N` | `src/images/`, см. раздел ниже |
| Блокировка перевода в `review` при визуальном дубле до решения редактора | `src/images/duplicates.ts` |
| Замена изображения: новые URL производных при неизменном URL карточки | `src/images/pipeline.ts`, `upload-hooks.ts` |

Ключевые инварианты, которые обязаны сохраняться при любой правке:

- новая запись создаётся только в `draft` с `noindex` и вне sitemap;
- в `published` и в `index,follow` запись переводит только человек с ролью
  `admin`, и никогда не автоматика, расписание или сервисный аккаунт;
- URL записи после первой публикации меняется только вместе с одиночным 301, а
  критерий «публиковалась» — `publishedAt`, не текущий статус (иначе адрес
  менялся бы в два шага через `draft`);
- URL файла постоянен: имя и суффикс `-N` присваиваются один раз и хранятся, а
  ключ производной меняется только вместе с ревизией — хешем БАЙТОВ;
- `seo-history` фиксирует автора каждого изменения SEO-полей.

**Отказ на уровне поля в Payload молчаливый**: значение удаляется из входных
данных, на его место возвращается прежнее, запрос отдаёт 200. Защита при этом
работает, но внешний клиент принял бы это за успех. Поэтому каждое правило,
закрытое доступом к полю, продублировано ГРОМКОЙ ошибкой в `beforeOperation` —
единственной фазе, где видна сама попытка, пока данные ещё сырые.

Не реализовано (отдельные задачи следующих этапов):

| Что | Задача |
|---|---|
| проверка дублей title/description по каталогу | Э5-01 |
| дашборд SEO-здоровья, выгрузка CSV, фоновая проверка ссылок | Э5-03…Э5-05 |
| перегенерация sitemap хуками при публикации, переносе и удалении | Э4-05 |
| ограничение частоты запросов для API-ключа (Ч-14) | Э6-03 |
| 2FA для администраторов | этап 7 |

## Изображения и хранилище (задачи Э2-04…Э2-06)

Решение Ч-03: S3 снят с обязательных, до переезда хранилище — **локальная ФС за
интерфейсом** `ImageStorage` (`src/images/storage.ts`). Замена реализации на S3
не должна трогать ни хуки, ни коллекции.

Две коллекции:

- `card-images` — файлы открыток. `upload` с `disableLocalStorage: true`: файлы
  пишет адаптер, а маршрут файла Payload закрыт явным обработчиком (404).
  Иначе оригинал был бы доступен по предсказуемому
  `/api/card-images/file/<имя>` — запрещено ТЗ §6.1;
- `image-name-claims` — реестр когда-либо выданных имён файлов. Не создаётся, не
  правится и **не удаляется** снаружи: удаление строки освободило бы суффикс
  `-N`, и уже выданный путь достался бы другому изображению.

Раскладка объектов:

```text
<IMAGE_STORAGE_DERIVATIVES_ROOT>/cards/<revision>/<имя>[-N]-<ширина>.<avif|webp|jpg>
<IMAGE_STORAGE_ORIGINALS_ROOT>/originals/<32 hex>.<ext>
```

Корни задаются окружением, дефолтов нет; корень оригиналов обязан лежать ВНЕ
корня производных — иначе адаптер не создаётся (условие C4). Относительное
значение разрешается от корня монорепозитория, а не от рабочего каталога.

| Переменная | Смысл |
|---|---|
| `IMAGE_STORAGE_DERIVATIVES_ROOT` | корень публичных производных; это дерево отдаёт `apps/web` по `/media/...` |
| `IMAGE_STORAGE_ORIGINALS_ROOT` | корень оригиналов; по HTTP не отдаётся никогда |

### Контракт для `apps/web` (задача Э2-04b, этап 3)

CMS обеспечивает раскладку файлов и заголовки, но НЕ маршрут. `apps/web` обязан:

- отдавать `GET /media/<ключ>` из `IMAGE_STORAGE_DERIVATIVES_ROOT` (только
  чтение, без листинга каталогов);
- ставить `Cache-Control: public, max-age=31536000, immutable` и `Content-Type`
  по расширению — оба значения берутся из `derivativeCacheHeaders`
  (`src/images/storage.ts`), а не переписываются строкой;
- отклонять любой путь, который после разрешения выходит за пределы корня;
- никогда не монтировать под `/media` корень оригиналов;
- собирать абсолютные адреса (JSON-LD `contentUrl`, image sitemap) единственным
  хелпером над `SITE_URL` — `derivativeAbsoluteUrl`;
- брать путь, дескриптор `w` в `srcset` и атрибуты `width`/`height` из
  сохранённого `variants[]` записи, а не пересчитывать из настроек (условие C8).

### Чтение данных из `apps/web` (контракт этапа 3)

Метаданные изображений (`card-images`) читаются **только аутентифицированным**:
иначе через API можно было бы перечислить производные ещё не опубликованных
открыток, а черновик публично недоступен по определению. То же у контента:
анонимному запросу `cards` и `collections` отдаются только записи в `published`
(ограничение возвращается запросом `Where`, а не логическим значением — подобрать
параметры и получить черновик нельзя).

Отсюда контракт для `apps/web`: страницы собирает СЕРВЕР — через Local API
Payload (`getPayload` + `payload.find`, `overrideAccess` по умолчанию) либо под
сервисным ключом. Требование «контент и первые изображения присутствуют в HTML
без выполнения JS» это не нарушает: HTML собирается на сервере, а браузеру
достаётся готовая разметка. Если публичный рендер упёрся в 403 — правильный ход
не открывать доступ анонимному клиенту, а перенести запрос на серверную сторону.

### Проверка на живой базе

Юнит-тесты проверяют правила, но фазы хуков, транзакции и access control полей
работают только на поднятом ядре. Для этого есть два смоука; оба удаляют за собой
все записи и файлы и не оставляют ни одной опубликованной записи:

```bash
pnpm --filter @otkritka/cms exec payload run ./scripts/smoke-etap1.ts   # 52 проверки
pnpm --filter @otkritka/cms exec payload run ./scripts/smoke-etap2.ts   # 36 проверок
```

- `smoke-etap1.ts` — статусная модель, права ролей, пакетные операции (Ч-07,
  включая отказ на пакетное СНЯТИЕ с публикации по фильтру и на одно решение о
  судьбе URL для всей выборки), запрет года в адресе, обязательность явной роли
  пользователя, неизменяемость URL с одиночным 301, перенос поддерева подборок,
  журнал истории. Карточки в нём получают изображения разных композиций: требование
  полноты `image` включилось с Э2-04, а разные композиции не задевают проверку
  визуальных дублей и не смешивают два правила в одном сценарии;
- `smoke-etap2.ts` — загрузка, полный набор производных и pHash, суффикс `-N`
  (включая «после удаления номер не переиспользуется»), недоступность оригинала,
  блокировка review при визуальном дубле, права на замену, замена изображения и
  уборка файлов.

Оба скрипта обязаны давать зелёный итог. Закоммиченный смоук, который заведомо
падает, — ловушка: следующий агент прочитает его вывод как реальное состояние
проекта.

## Замечание про Next.js 16

Next 16 расходится с обучающими данными моделей: API, соглашения и структура
файлов отличаются от предыдущих версий. Перед правкой маршрутов читайте
документацию в `node_modules/next/dist/docs/` (в монорепозитории пакет `next`
виден из `apps/cms`, а не из корня), а типы Payload — в
`node_modules/payload/dist/`.

Автоматическую генерацию `AGENTS.md` и `CLAUDE.md`, которую `next dev` делает по
умолчанию, мы отключили (`agentRules: false`): вложенный `CLAUDE.md` — это
дополнительные инструкции для агентов, появившиеся побочным эффектом
dev-сервера, а в проекте единственный `CLAUDE.md` лежит в корне.

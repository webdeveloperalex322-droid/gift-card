# apps/web — Astro

Владелец: агент `astro-web`.

Установлено на задаче Э3-01: astro 7.2.4 + @astrojs/node 11.1.4 в режиме
`mode: 'middleware'` (было `standalone` — почему изменено, ниже).

## Режим рендеринга

«Гибридный режим» отдельным значением `output` в astro 7 не выражается — в типе
конфига остались `'static'` и `'server'`. Актуальная форма гибрида: `output:
'static'` вместе с адаптером, а маршрут, которому нужен SSR, объявляет
`export const prerender = false`. Выбор и его обоснование зафиксированы
комментарием в `astro.config.mjs`.

## Кто обрабатывает запрос

```text
node dist/server/entry.mjs        (src/server/entry.mts)
  -> decideRequestTarget()        (src/routing/path-policy.ts)  решение по СЫРОЙ цели
  -> производные /media/<ключ>    (src/server/media-files.ts)   файлы хранилища, без листинга
  -> статика из dist/client       (src/server/static-files.ts)  только файлы, без редиректов
  -> обработчик Astro             (dist/server/astro-app.mjs)   SSR-маршруты и 404
```

Адаптер собран в режиме middleware и **сервер не поднимает**. Сервер, порядок
обработки и отдачу статики держит `src/server/`. Это не архитектурное
украшательство: в `standalone` статический обработчик адаптера отвечал раньше
пользовательского middleware, и три класса путей отвечали мимо нашего кода —

| Путь | Было (standalone) | Стало |
|---|---|---|
| `/%2F`, `/%2F/` | бесконечный цикл 301 (`/%2F` ⇄ `/%2F/`) | 400 |
| `////` | три перехода: `///` → `//` → `/` | один 301 на `/` |
| `/index.html` | 200 с содержимым главной (второй адрес) | 404 |
| `/<путь>.html` | 200 с содержимым страницы | 404 |
| `/<каталог>/` в `dist/client` | 301 «минус один слеш», поведение зависело от платформы | 301 по нашему правилу слеша, каталог не отдаётся |

Замеры и механизм каждого случая — в шапке `src/routing/path-policy.ts`.

`dist/server/entry.mjs` — имя-контракт: на него смотрят смоук, стенд SEO-приёмки
(`tests/seo/support/serve-built-web.mjs`) и `astro preview`. Оно сохранено:
приложение Astro переехало в `dist/server/astro-app.mjs` (`build.serverEntry`).
Сервер поднимается на импорте; отключается как у адаптера —
`ASTRO_NODE_AUTOSTART=disabled`, тогда модуль только экспортирует `handler`.

### Контракт запуска собранного сервера

```bash
pnpm --filter @otkritka/web run build
pnpm --filter @otkritka/web run start      # = node ./scripts/start-server.mjs
```

`start` запускает точку входа **через обёртку** `scripts/start-server.mjs`, а не
`node ./dist/server/entry.mjs` напрямую. Причина замерена, а не предположена:
после смены активной версии Node сервер стал падать первым же обращением к базе —

```text
Cannot find module 'drizzle-kit/api'
```

Механизм: адаптер Postgres у Payload подтягивает `drizzle-kit/api` динамическим
импортом при накате схемы, а пакет лежит в виртуальном хранилище pnpm
(`<корень>/node_modules/.pnpm/node_modules`), которое не входит в цепочку
разрешения от `apps/web/dist/server/chunks/`. Дыру закрывал `NODE_PATH`, который
pnpm прокидывал сам; после смены версии Node он перестал приходить, и падение
выглядело как «сломался билд», хотя сломалось разрешение модулей. Обёртка
находит виртуальное хранилище и добавляет его в `NODE_PATH` дочернего процесса;
если хранилища нет (не pnpm-овская раскладка), она ничего не добавляет.
Значений по умолчанию обёртка не подставляет вовсе — `SITE_URL`, `HOST`, `PORT`
проходят сквозь неё как есть.

Смежное: у `apps/cms` есть параметр `PAYLOAD_DB_PUSH` (пустое значение =
«накатывать», пока в проекте нет миграций). Именно накат схемы и тянет
`drizzle-kit/api`, поэтому `PAYLOAD_DB_PUSH=false` тоже убирает симптом — но это
другое решение: оно выключает накат, а не чинит разрешение модулей. Менять
дефолт до появления миграций нельзя (см. `.env.example`), поэтому контракт
запуска держится на обёртке.

Запуск в обход обёртки (`node ./dist/server/entry.mjs`) остаётся рабочим ровно
там, где `NODE_PATH` уже задан снаружи, — например внутри `pnpm run`, который его
прокидывает. Смоуки (`smoke:pages`, `smoke:slash`, `smoke:media`) поднимают
точку входа именно так, из процесса, запущенного через `pnpm`.

## Правила URL (решение Ч-21 и «Один материал — один путь»)

Единая форма — БЕЗ завершающего слеша. Правило живёт в ОДНОМ месте:

- `src/routing/path-policy.ts` — чистая функция `decideRequestTarget`: отдать,
  одиночный 301, 404, 400 или «не обслуживаем» (маршруты админки);
- `src/server/front-door.ts` — превращение решения в HTTP-ответ;
- `src/middleware.ts` — то же решение для входов без нашего сервера
  (`astro dev`, встраивание обработчика в чужой сервер).

Границу «страница или файл» даёт `isPageRoute` из `@otkritka/shared`, сверку
канонической формы — `canonicalizePath` оттуда же. Локальных копий этих правил
здесь нет и быть не должно. Одно расхождение зафиксировано письменно в шапке
`packages/shared/src/routes.ts`: `canonicalizePath` пустые сегменты в середине
схлопывает (это про путь, который мы строим сами), а запрос с пустым сегментом
сервер отвергает 404 (это про цель запроса извне).

Проверки:

```bash
pnpm exec vitest run tests/unit/web-path-policy.test.ts   # решение по цели запроса
pnpm --filter @otkritka/web run build
pnpm --filter @otkritka/web run smoke:slash               # 26 классов путей на живом сервере
```

Смоук запрашивает цели через `node:http` с сырым `path`, а не через `fetch`:
`fetch` разбирает адрес парсером URL и часть форм (`/%2e`) до сервера не доехала
бы в исходном виде.

### Известные особенности окружения (замерено на astro 7.2.4)

- **Приёмку SEO и смоук гонять только против СОБРАННОГО сервера.** В `astro dev`
  при `trailingSlash: 'never'` Astro вместо 301 показывает
  страницу-предупреждение со статусом 404. Порядок: `astro build`, затем
  `pnpm --filter @otkritka/web run start`.
- **Пререндер запрашивает страницу по имени ФАЙЛА.** При `build.format: 'file'`
  во время сборки путь выглядит как `/o-proekte.html`. Наша политика такой адрес
  справедливо считает не-адресом, поэтому middleware пропускает заранее
  отрендеренные маршруты без проверки (`context.isPrerendered`). Без этого
  пререндер молча не создаёт файлы: «file not created, response body was empty».
- **`localhost` на Windows.** Node привязывает `localhost` к IPv6-петле
  (`[::1]`), поэтому инструмент, который резолвит `localhost` в `127.0.0.1`, до
  сервера не доходит. Для детерминированного адреса: `astro dev --host
  127.0.0.1`, а для собранного сервера — `HOST=127.0.0.1`.

## Проверка типов и сборка

Две программы TypeScript, потому что у файлов apps/web два разных рантайма:

| Проект | Что проверяет | Разрешение модулей |
|---|---|---|
| `tsconfig.json` (`astro check`) | шаблоны `.astro`, `src/middleware.ts`, `src/data`, `scripts`, всё под `src` | `Bundler` (пресет Astro) |
| `tsconfig.node.json` (`tsc -b`) | `src/routing`, `src/server` + emit в `dist` | `NodeNext` |

Отсюда же следует, где лежат юнит-тесты слоя данных: рядом с ним
(`src/data/data-access.test.ts`), а не в `tests/unit/`. Модули `src/data`
намеренно не входят в composite-проект `tsconfig.node.json` (они импортируют
`.ts` из другого пакета и живут только внутри Vite), а тест из `tests/unit/`
обязан импортировать файл, входящий в один из проектов, на которые ссылаются
тесты, — иначе `tsc -b` отказывает (TS6307). Тесты `src/routing` и `src/server`
остаются в `tests/unit/`: эти модули в composite-проект входят.

Отсюда требование: **относительные импорты в `src/routing` и `src/server` — только
с расширением `.js`** (для `.mts` — `.mjs`). Форма без расширения прошла бы
`astro check` и упала бы на `pnpm check`. Требование записано в шапке
`src/routing/path-policy.ts`.

Скрипт `build` = `astro build && tsc -b tsconfig.node.json`, порядок значим:
`astro build` чистит `dist`, поэтому tsc идёт вторым, а файл состояния его
инкрементальной сборки лежит внутри `dist` — иначе после очистки tsc доложил бы
«всё актуально», не восстановив точку входа.

## Абсолютные URL

Только через `canonicalUrlFor` (`src/routing/canonical.ts`), а он — через
единственный хелпер `buildAbsoluteUrl` из `@otkritka/shared`. `site` в
`astro.config.mjs` НЕ задан намеренно: `Astro.site` стал бы вторым источником
хоста. Окружение читается в рантайме (`src/server-env.ts`), а не запекается в
сборку.

## Инварианты рендеринга (`CLAUDE.md`)

- title, H1, canonical, хлебные крошки, основной текст, ссылки и первые
  изображения — в HTML-ответе сервера; страница полноценна при отключённом JS;
- навигация только `<a href>`, hash-маршрутизация запрещена;
- клиентский JS — только точечные острова; в `BaseLayout.astro` его нет вовсе,
  панель разработчика Astro выключена в конфиге;
- пагинация с постоянными URL, бесконечная лента запрещена.

## Чего здесь ещё нет

`sitemap.xml`, `robots.txt` и middleware, применяющее 301-редиректы из коллекции
`redirects`, — этап 4. Контентные маршруты (`/otkrytki`, `/podborki`,
информационные страницы, главная) — задачи Э3-05…Э3-11. Единственный маршрут
сейчас — техническая заглушка на `/` с директивой `noindex,follow`.

Своя страница 404 — задача Э3-11. Пока её нет, ответ 404 приходит из двух мест:
на путях, отвергнутых политикой, — из встроенной заглушки
`src/server/front-door.ts`; на несовпавших маршрутах — из страницы Astro по
умолчанию (`<html lang="en">`, без навигации). Условие, при котором это станет
одной страницей: `src/pages/404.astro` должна быть пререндеренной, тогда
`dist/client/404.html` читают оба пути.

## Производные изображений: `/media/<ключ>` (задача Э2-04b)

Файлы отдаются из корня `IMAGE_STORAGE_DERIVATIVES_ROOT` — того же, куда их
пишет `apps/cms` (решение Ч-03: S3 отложен, хранилище — локальная ФС за
адаптером). Дефолта у корня нет: незаданное значение даёт внятную ошибку на
запросе файла, а не «пустые» изображения.

| Правило | Где живёт |
|---|---|
| форма ключа, `Cache-Control: public, max-age=31536000, immutable`, `Content-Type` | `@otkritka/images/media` — один источник на web и cms |
| «наш путь / не наш / не адрес» | `src/server/media-files.ts` (`decideMediaRequest`) |
| «файл лежит под корнем» (лексически и на диске) | `src/server/static-files.ts` (`resolveServableFile`) |
| корень отдачи из окружения | `src/server/media-files.ts` (`resolveMediaRoot`) |

Что закрыто по построению: каталог не отдаётся ни списком, ни индексным файлом
(у каталога нет расширения, поэтому он не проходит форму ключа); оригиналы
недостижимы — их корень лежит ВНЕ корня производных (условие C4), поэтому даже
корректно сформированный ключ вида `originals/<id>.jpg` разрешается внутри
дерева производных и даёт 404; dot-сегменты и любые формы `%2F`/`%5C`
отклоняются политикой пути до этого слоя (400).

Ветка `/media` есть и в `src/middleware.ts` — она нужна только `astro dev`, где
нашего сервера нет: без неё изображения в dev не открывались бы, потому что
файлы лежат вне `public/`. Своих правил у неё нет, она зовёт те же функции.

```bash
pnpm --filter @otkritka/web run build
pnpm --filter @otkritka/web run smoke:media   # 32 проверки на живом сервере
```

## Чтение контента: слой доступа к данным (задача Э3-02)

Шаблоны читают CMS только через `src/data/` — и только правами АНОНИМА:
`overrideAccess` в значении false, пользователь не передаётся, поэтому фильтр
«только `published`» ставит access control Payload, а не `apps/web`. Включение
`overrideAccess` в `apps/web` запрещено и проверяется текстовым тестом
(`src/data/data-access.test.ts`).

| Модуль | Назначение |
|---|---|
| `src/data/payload-client.ts` | Local API Payload, один экземпляр на процесс; обоснование выбора против HTTP под API-ключом |
| `src/data/read-scope.ts` | область чтения, постусловие по статусу, номер страницы пагинации |
| `src/data/queries.ts` | чистые запросы: что именно спрашивается у Payload |
| `src/data/content.ts` | выполнение запросов, типы результата из `@otkritka/cms/types` |

Доступ — Local API (`getPayload` + `@otkritka/cms/config`), а не HTTP к CMS:
API-ключ наследует роль своего пользователя, а обе роли проекта видят черновики,
поэтому публичный рендер обязан читать без ключа. Слой работает ТОЛЬКО внутри
сборки Astro (Vite): конфиг Payload — это `.ts` из другого пакета, и входной
сервер (`src/server/*`, настоящий Node ESM) его импортировать не может.

```bash
pnpm exec vitest run apps/web/src/data/data-access.test.ts
pnpm --filter @otkritka/web run smoke:data    # 21 проверка на живой базе, с уборкой
```

Известный пробел, важный для Э3-05…Э3-09: метаданные изображений
(`card-images.variants[]` — ключи, ширины, высоты) этим слоем недостижимы.
Доступ на чтение у коллекции — `authenticatedAccess`, поэтому аноним получает
`Forbidden`, а население связи при `depth > 0` подставляет идентификатор. Значит
`srcset` из сохранённых вариантов (условие C8) собрать пока нечем — вопрос
владельцу `apps/cms`, зафиксирован в отчёте задачи Э3-02.

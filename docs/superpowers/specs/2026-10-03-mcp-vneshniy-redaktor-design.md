# MCP-слой для внешнего AI-редактора

Дата: 2026-10-03. Статус: дизайн утверждён человеком в чате, спека на вычитке.

## 1. Задача

Дать внешней LLM (не Claude Code, работающей в этом репозитории, а облачному
чату или CLI-агенту на стороне) возможность **создавать и редактировать
категории и карточки на продакшене** — через MCP, по сети, своими правами.

Граница автоматизации не сдвигается ни на сантиметр: агент доводит контент до
`review`, решение о публикации и об `index,follow` принимает человек (п. 7.1 и
п. 23 SEO ТЗ, ТЗ §9, Ч-07). MCP-слой эту границу не ослабляет и не дублирует —
он её наследует, потому что ходит через те же access control и хуки.

ТЗ §9 и §15 относили MCP-обёртку к «этапу 2 развития»
(`docs/plan-etapov.md:284`). Решением человека 2026-10-03 она переводится в
текущий объём. Формулировка операций взята из ТЗ §9 дословно: «создай черновик
карточки», «прикрепи к подборкам», «проверь дубли», «переведи в review».

## 4. Архитектура

```
Внешний клиент (Gemini/Antigravity CLI, Claude Code, свой скрипт)
   │  POST https://dobrye-otkrytki.ru/api/mcp
   │  Authorization: Bearer <API-ключ ai-editor>
   ▼
nginx:  location ^~ /api/mcp { auth_basic off; }      ← единственное снятие Basic Auth
   ▼
apps/cms/src/mcp/
   endpoint.ts      Payload Endpoint: метод, Origin, токен, лимит попыток
   protocol.ts      JSON-RPC и две эры MCP (см. §5), без знания о предметной области
   schema.ts        декларация аргументов → JSON Schema + рантайм-валидатор
   registry.ts      список инструментов: имя, описание, схема, аннотации
   tools/*.ts       по файлу на инструмент; предметная логика; gateway аргументом
   gateway.ts       ЕДИНСТВЕННОЕ место касания Payload
   ▼
Payload Local API, всегда overrideAccess: false + user = владелец ключа
   ▼
access control + хуки + seo-history
```

### 4.1 Шлюз как устройство, а не как дисциплина

Local API по умолчанию ходит с `overrideAccess: true`, то есть мимо всех прав —
это прямо описано в шапке `src/access/policies.ts`. Размещение внутри `apps/cms`
(Ч-35e) означает, что обойти границу автоматизации можно одной забытой строкой.
Закрывается тремя средствами, и каждое нужно отдельно:

1. **`gateway.ts` — единственный файл слоя, импортирующий тип `Payload`.** Он
   экспортирует узкий набор операций (`findCards`, `findCollections`,
   `createCard`, `updateCard`, `createCollection`, `updateCollection`,
   `findCardImages`) и в каждой жёстко задаёт `overrideAccess: false` и `user`.
   Параметра, которым это можно переключить, у функций шлюза нет — не «по
   умолчанию false», а отсутствует как возможность.
2. **Тест-страж** (`src/mcp/gateway-isolation.test.ts`): читает все файлы
   `src/mcp/**`, кроме `gateway.ts`, и падает, если встречает `req.payload`,
   `payload.`, `overrideAccess` или `Local API`. Правило, живущее в комментарии,
   нарушается при первой правке; правило, живущее в тесте, — нет.
3. **Инструменты получают шлюз аргументом.** Отсюда и подменяемость в юнит-тестах,
   и невозможность «дотянуться до Payload мимо шлюза» — другого доступа у них нет.

Пользователь для шлюза — **владелец предъявленного ключа**, загруженный из базы, а
не константа: автор правки в `seo-history` обязан совпадать с владельцем ключа.
При этом **канал открыт только роли `ai-editor`** — так читается Ч-35f («API-ключ
существующего аккаунта `ai-editor`»), и проверка стоит до шлюза.

Правка после ревью 2026-10-03: в первой редакции здесь стоял довод «права
принадлежат аккаунту, а не каналу», и принимался ключ любого аккаунта. Довод
неверен по последствиям — ключом `admin` внешняя модель правила бы тексты уже
опубликованных индексируемых страниц и меняла изображение опубликованной карточки
мимо `review`. Расширение канала на другие роли требует отдельного решения
человека.

### 4.2 Идемпотентность

У `cards` и `collections` есть уникальное поле `sourceImportKey` и готовый
механизм доверенного ключа импорта (`src/import/source-import-identity.ts`).
Инструменты создания принимают обязательный `externalKey`; повторный вызов с тем
же ключом возвращает существующую запись и признак `created: false`.

Без этого первый же таймаут сети даёт вторую карточку: LLM ретраит охотно, а
`cards` — коллекция, где лишняя запись означает лишний canonical URL и занятый
навсегда claim пути.

## 5. Протокол

Реализуется **дуальная эра** (термин спеки MCP): и ревизия `2026-07-28`
(stateless, метаданные в каждом запросе), и ревизии с рукопожатием `initialize`
(`2025-03-26` … `2025-11-25`). Причина простая: Gemini/Antigravity CLI и Claude
Code на момент написания ходят legacy-рукопожатием, а новая ревизия — то, куда
двигаются все клиенты. Сервер выбирает эру по форме запроса: `initialize` →
legacy; `_meta.io.modelcontextprotocol/protocolVersion` → modern.

Транспортные требования ревизии `2026-07-28`, реализуемые буквально:

| Требование | Реализация |
|---|---|
| единственная ручка, только POST | `/api/mcp`; GET и DELETE → `405` |
| валидация `Origin` | присутствует и не из белого списка → `403` (защита от DNS rebinding) |
| `Accept` клиента содержит `application/json` и `text/event-stream` | проверяется; ответ всегда `application/json` — спека это разрешает прямо |
| `MCP-Protocol-Version` обязателен и обязан совпасть с `_meta` | расхождение → `400` + JSON-RPC `-32020` `HeaderMismatch` |
| `Mcp-Method` обязателен, `Mcp-Name` обязателен для `tools/call` | то же: расхождение или отсутствие → `-32020` |
| `Mcp-Name` может быть в sentinel-кодировке `=?base64?…?=` | декодируется перед сравнением с телом |
| неподдерживаемая версия | `400` + `-32022` с `data.supported` |
| неизвестный метод | `404` + `-32601` |
| нотификация (без `id`) | `202 Accepted` без тела |
| `server/discover` обязателен | реализуется: версии, `serverInfo`, `capabilities.tools` |
| `Mcp-Session-Id`, `Last-Event-ID` | игнорируются, не выдаются и не эхом |

SSE не реализуется вовсе: ни один инструмент не отдаёт прогресс, а ответ одним
JSON-объектом спека разрешает. Отсюда и отсутствие адаптера между Web-`Request`
Payload-ручки и Node-стримами SDK — именно этот зазор делал официальный SDK
неудобным здесь, и именно поэтому новых зависимостей (`@modelcontextprotocol/sdk`,
`zod`) не добавляется.

Схемы аргументов объявляются один раз (`schema.ts`) декларативно, а из
декларации выводятся И JSON Schema для `tools/list`, И рантайм-валидатор. Две
независимые записи одной истины означали бы инструмент, чья схема обещает одно, а
проверка требует другого.

Публикация, `index/noindex`, `canonical`, смена slug после публикации,
редиректы, sitemap, `updatedContentAt`, пользователи и ключи, удаление
опубликованных записей.

Отсутствие инструмента — только первый запрет. Второй, независимый, — отказ
access control на том же действии, уже реализованный и доказанный живыми тестами
`tests/api/`. Одного запрета было бы мало: инструмент можно добавить по
невнимательности, права — нет.

## 7. Аутентификация и периметр прода

### 7.1 Сеть

На 2026-10-03 прод в закрытом режиме: Basic Auth висит на всём `server`-блоке
(`deploy/nginx/dobrye-otkrytki.ru.conf`), плюс `X-Robots-Tag: noindex, nofollow`
на все ответы. Добавляется ровно одна локация:

```nginx
# MCP-вход внешней LLM. auth_basic off НАМЕРЕННО: клиент не может предъявить
# и Basic, и собственный токен — заголовок Authorization один, и Basic его
# занимает. ^~ даёт приоритет над location /api и location /, поэтому
# остальной периметр (включая /api/users, /api/graphql, /admin) не ослабляется.
location ^~ /api/mcp {
    auth_basic off;
    proxy_pass http://127.0.0.1:3011;
    include /etc/nginx/snippets/otkritka-proxy.conf;
}
```

Это единственное место во всей конфигурации, где снимается Basic Auth (кроме
ACME-челленджа), и снимается он для одного пути.

### 7.2 Проверка токена

Порядок в обработчике фиксирован и важен: **сначала дешёвые проверки, потом
обращения к базе.** Иначе ручка сама становится каналом исчерпания ресурсов —
тот же довод, по которому rate limit в проекте считает отпечаток ключа, не
спрашивая Postgres.

1. метод не POST → `405`, тела нет;
2. `Origin` присутствует и не разрешён → `403`;
3. нет `Authorization: Bearer <...>` → `401` + `WWW-Authenticate: Bearer`;
4. бакет неудачных попыток для хеша IP исчерпан → `429` + `Retry-After`;
5. поиск владельца ключа по тому же HMAC-отпечатку, которым Payload заполняет
   `users.apiKeyIndex`, **плюс** проверка `enableAPIKey === true`. Своя
   стратегия аутентификации Payload флаг не смотрит вовсе (разбор — в шапке
   `src/collections/users.ts`), поэтому здесь он проверяется явно: иначе
   «отозванный» ключ продолжал бы работать через MCP;
6. владелец не найден → `401` без подробностей и с расходом попытки.

Что принципиально:

- **сравнение постоянного времени.** Отпечаток ключа сравнивается
  `crypto.timingSafeEqual`, не `===`;
- **ответ 401 одинаков** для «нет ключа», «ключ не найден», «ключ отозван».
  Различимые ответы — оракул для перебора;
- **токен не попадает в логи никогда.** В журнал идёт отпечаток, как в
  rate-лимитере;
- **лимит попыток по IP нужен отдельно от Ч-14.** Существующий лимитер считает
  только запросы С ключом; неудачная попытка ключа не несёт, и перебор он не
  видит. Реализуется вторым хранилищем бакетов над тем же `token-bucket.ts`,
  без второй реализации алгоритма;
- **`X-Robots-Tag: noindex`** на ответах ручки; в `robots.txt` и sitemap путь не
  попадает — по той же причине, по которой не публикуется путь админки (Ч-22).

### 7.3 Почему ChatGPT пока не подключится

ChatGPT для удалённого MCP принимает только пользовательский OAuth 2.1 (с
metadata-документами или Dynamic Client Registration) либо «без
аутентификации»; machine-to-machine гранты, API-ключи и кастомные заголовки он
не поддерживает. Вариант «без аутентификации» для ручки, которая пишет в базу
прода, неприменим: URL в таких интеграциях попадает в логи, скриншоты и историю
браузера, поэтому неизвестность адреса защитой не является.

Следствие принято сознательно (Ч-35d): до этапа OAuth подключаются
Gemini/Antigravity CLI, Claude Code и любой свой скрипт. Этап OAuth — отдельная
спека: `.well-known/oauth-protected-resource`,
`.well-known/oauth-authorization-server`, экран согласия, `authorize`/`token`,
PKCE, refresh, регистрация клиента. Он ничего в этом дизайне не ломает: меняется
шаг 3–5 из §7.2, остальное остаётся.

## 8. Контракт ответа и отказа

Главная ловушка — не в MCP, а в Payload: **отказ на уровне поля молчаливый.**
Поле вырезается из входных данных, на его место встаёт прежнее значение, ответ
`200`. Это разобрано в шапке `src/access/policies.ts` и лежит в основе
разделения `silent`/`loud` в `tests/api/README.md`. Для внешней модели это
означает успех на запрещённой операции и ложный рапорт человеку.

Поэтому каждый пишущий инструмент работает в три шага: **записать → перечитать →
сравнить с запрошенным.** Ответ содержит:

- `applied` — какие поля фактически приняты;
- `ignored` — какие были запрошены и не применились, с причиной;
- `path` — итоговый путь записи, чтобы модель могла проверить результат;
- `created` — признак идемпотентного попадания в существующую запись.

Непустой `ignored` — **ошибка инструмента** (`isError: true`) с внятным текстом,
а не успех с оговоркой. Запрещённое по правам (попытка `published`, robots,
редирект) отклоняется до обращения к базе, с указанием, что это решение человека
и где оно принимается.

Выборки усекаются по лимиту и всегда сопровождаются признаком усечения — как
`scanTruncated` в дашборде. Молча обрезанный список означает, что модель сочтёт
тему готовой, не увидев остатка.

## 9. Переменные окружения

| Переменная | Назначение | Дефолт |
|---|---|---|
| `MCP_ENABLED` | включение ручки целиком | `false` — выключено, пока не включили явно |
| `MCP_ALLOWED_ORIGINS` | белый список `Origin` через запятую; пусто = запрос с `Origin` отвергается | пусто |
| `MCP_AUTH_FAILURE_LIMIT` | попыток `401` на IP в окне | `10` |
| `MCP_AUTH_FAILURE_WINDOW_SECONDS` | окно для предыдущей | `60` |

Мусорное значение валит старт приложения, как `API_RATE_LIMIT_*` и
`PAYLOAD_ADMIN_PATH`: тихий возврат к дефолту означал бы, что настройку
применили, а она не применилась. Выключателя у лимита попыток нет — ноль и
отрицательные значения отвергаются.

`MCP_ENABLED=false` по умолчанию — не перестраховка: ручка открывает сетевой
вход, который раньше был закрыт Basic Auth, и появление её в репозитории не
должно означать её появление на проде.

## 10. Тесты

Три уровня, ни один не заменяет другой.

**Юнит (`src/mcp/**/*.test.ts`)**: разбор JSON-RPC и обеих эр, валидация
заголовков и всех кодов ошибок из §5, вывод JSON Schema из декларации, формы
аргументов, идемпотентность по `externalKey`, тексты отказов, страж изоляции
шлюза, разбор env.

**Живые негативные (`tests/api/mcp-*.test.ts`)**, по схеме каталога: прочитать
состояние правами системы → попытка через MCP → прочитать после → доказать, что
операция вообще выполнилась. Сценарии: `published` через MCP, robots, canonical,
смена slug после публикации, создание редиректа, правка пользователя и ключа,
`updatedContentAt`, удаление опубликованной карточки. Плюс свои: `401` без
токена, `401` с неизвестным токеном, `401` с отозванным (`enableAPIKey: false`)
ключом, `429` при переборе, `405` на GET, `403` на чужой `Origin`, автор правки
в `seo-history` — владелец ключа.

**Приёмка**: `pnpm verify` целиком, включая `pnpm test:seo` — MCP трогает
коллекции, а это один из четырёх триггеров обязательной SEO-приёмки из
`CLAUDE.md`.

## 11. Риски и принятые цены

| Риск | Решение |
|---|---|
| Local API мимо прав | закрыт устройством (§4.1), а не дисциплиной; страж в тестах |
| перебор Bearer-токена | лимит попыток по IP, одинаковый `401`, сравнение постоянного времени |
| новый сетевой вход на проде | одна локация, `MCP_ENABLED=false` по умолчанию, `X-Robots-Tag: noindex` |
| prompt injection через тексты от внешней модели | тексты — данные, не инструкции; проходят те же валидации; последнее слово у человека на `review` |
| своя реализация протокола вместо SDK | буквальное следование спеке `2026-07-28` + дуальная эра, каждый код ошибки покрыт юнит-тестом; цена — ручное отслеживание следующих ревизий |
| ChatGPT не подключается | принято (Ч-35d), снимается этапом OAuth |
| дубли при ретраях | обязательный `externalKey` поверх существующего `sourceImportKey` |

## 12. Что не входит

OAuth 2.1 и подключение ChatGPT; загрузка байтов изображений; публикация и
`index,follow` любым способом; редиректы; SSE, прогресс, sampling, elicitation,
resources, prompts, подписки; MCP-обёртка для локального stdio.

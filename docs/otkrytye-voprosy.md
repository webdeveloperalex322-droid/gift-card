Блокирует Э2-04, Э2-05, Э2-06 — весь остаток этапа 2. Нужно:

1. провайдер, `S3_ENDPOINT`, `S3_REGION`;

### Детали, без которых на эти вопросы отвечать неудобно

**Ч-08, замеры пайплайна** (материал для подбора, не предложение значения; расстояние Хэмминга по 64 битам). Композиция «сетка»: перекодирование без потерь — 0, JPEG q80 — 4, ресайз до 640 — 6, яркость +12 % с q35 — 8. Другая композиция («кольца») — 30 в PNG и 24 в JPEG q80. **Но:** «похожие» держатся ниже 8 только на композиции «сетка»; на «кольцах» обычное перекодирование в JPEG q80 даёт уже 12, ресайз — 12, яркость с q35 — 10. Отсюда вилка `12 ≤ порог < 24`: значение, подобранное по одной композиции, будет либо пропускать дубли, либо давать ложные срабатывания. Окончательный выбор требует эталонной выборки (Ч-06).

Отдельно к Ч-08: DCT-pHash **не инвариантен к повороту** — поворот на 180° даёт 28, на 90° — 36. Повёрнутый дубль редактору по хешу не покажут ни при каком пороге. Это ограничение алгоритма, а не настройка.

**Ч-25, текущее поведение** (защита от тихой ошибки, не выбранная норма): литера, не давшая после таблицы и снятия диакритики ни одного допустимого символа, обрывает `slugify` целиком — результат пустой, валидатор его отклоняет, запись без slug не заводится. Отказ всей строки, а не пропуск литеры: иначе «Открытки для Наталії» дало бы `otkrytki-dlya-natali`, правдоподобный slug другого слова. Латиница с диакритикой при этом теряет диакритику (`Café → cafe`), одиночные комбинирующие метки отбрасываются (`İstanbul → istanbul`, «по́здравления» → `pozdravleniya`).

**Ч-28, обязательное условие C2** (требование контролёра `url-guard`, не вариант на выбор): `revision` меняется **только** при замене байтов изображения. Выводить её из `updatedAt`, версии записи или счётчика сохранений нельзя — каждое сохранение переписало бы URL всех производных. Привязка к содержимому (хеш байтов или id нового оригинала) делает незаметную смену URL структурно невозможной.

**Ч-09, смежное условие C7:** append-only по `IMAGE_WIDTHS` не покрывает случай мелкого исходника. Для источника 500 px при ширинах 640/960 рождается ключ `…-500.jpg`, а после **добавления** ширины 320 — операции, объявленной дешёвой, — fallback исчезает и ключ перестаёт воспроизводиться.

## 5. Решения человека, не заведённые отдельным номером

Всплыли при реализации этапа 2. Зафиксированы тестами, но **нормой не являются**:

1. **Ширина больше исходной** — не апскейлится, вариант пропускается. ТЗ этого случая не задаёт.
2. **Мелкий исходник** — если ни одна настроенная ширина не подошла, делается один вариант в натуральную ширину и поднимается признак `nativeWidthFallback`. Порог минимальной ширины на загрузке и политика «пускать ли такие изображения в публикацию» — за человеком: в пайплайне их нет намеренно, это решение модерации, а не кода.
3. **Уникальность ключа производной**: два изображения с одинаковым именем и одинаковой ревизией дают один ключ. Это прямое следствие контракта постоянства пути (счётчик сделал бы путь зависимым от состояния хранилища); уникальность обязан обеспечить Э2-05.

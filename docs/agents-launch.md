# Запуск агентов — инструкция оператора

Практическая часть: кого вызывать, чем именно, в каком порядке и что проверить
перед тем, как принять работу. Процесс и границы описаны в `agent_readme.md`,
требования — в `docs/seo-requirements.md`. При противоречии прав ТЗ.

Определения агентов лежат в `.claude/agents/*.md` и подхватываются Claude Code
автоматически при запуске из корня репозитория. Отдельной команды установки нет:
если файл на месте — агент доступен.

---

## 1. Состав

### Реализаторы — пишут код, каждый в своей папке

| Агент | Владеет | Зона |
|---|---|---|
| `astro-web` | `apps/web/` | роуты, шаблоны, крошки, пагинация, sitemap, robots, middleware редиректов, JSON-LD, вывод изображений |
| `payload-cms` | `apps/cms/` | коллекции, хуки `beforeChange`, access control, роли `admin`/`ai-editor`, `seo-history` |
| `images-pipeline` | `packages/images/` | sharp, AVIF/WebP/JPEG, размеры для srcset, pHash, имена файлов |
| `shared-core` | `packages/shared/` | транслитерация, валидация URL, `TRAILING_SLASH`, типы статусной модели |

### Редактор контента — пишет текст, не код

| Агент | Владеет | Зона |
|---|---|---|
| `content-editor` | записи в CMS, `docs/content/` | title, H1, description, вводный текст, alt, привязка к подборкам, перелинковка, `draft` → `review` |

### Контролёры — только читают, имеют право вето

| Агент | Проверяет | Обязателен, когда |
|---|---|---|
| `url-guard` | URL, canonical, одиночные 301, отсутствие цепочек, состав sitemap | тронуты slug, роут, canonical, редиректы, sitemap, правила URL в `shared` |
| `seo-auditor` | чек-лист п. 22, условия п. 5.1; владеет `tests/seo/` | тронуты шаблон, роутинг, sitemap, коллекции, вывод изображений |
| `perf-guard` | LCP/INP/CLS/TTFB, вес HTML, резервирование места, порядок загрузки | тронуты шаблоны, вывод изображений, скрипты рекламы, конфиг сборки |
| `reviewer` | запреты п. 23 и соглашения по коду | **всегда**, для любого дифа |

### Координатор

| Агент | Роль |
|---|---|
| `planner` | декомпозиция на назначения, порядок, точки вето, список решений для человека. Кода не пишет |

## 2. Кого вызвать

| Ситуация | Вызов |
|---|---|
| Правка в одном слое, владелец очевиден | сразу реализатора |
| Затронуто два слоя и больше | `planner`, затем реализаторов по его плану |
| Правка общего контракта (`packages/shared`) | `shared-core` первым, потом потребители |
| Текст, метаданные, alt, перелинковка | `content-editor` |
| «Где определён X», «что вызывает Y» | `Explore` — профильный агент не нужен |
| Проверить готовую работу | `reviewer` + профильные контролёры |
| Непонятно, что требует ТЗ | `planner`; если ТЗ молчит — вопрос человеку, не догадка |

Мелкая механическая правка в одном файле агента не требует: делайте напрямую и
переходите к протоколу завершения.

---

## 3. Из чего состоит постановка задачи

Агент **не видит** историю вашего диалога. Всё, что ему нужно, идёт в промпте.
Шесть обязательных блоков:

1. **Цель** — что должно работать после правки, а не какие файлы потрогать.
2. **Границы** — какие папки можно менять. За их пределами только чтение.
3. **Контекст** — куда смотреть: `CLAUDE.md`, пункт ТЗ, отчёт предыдущего агента.
4. **Критерий готовности** — какой тест или проверка это подтверждает.
5. **Точки вето** — каких контролёров вызвать перед завершением.
6. **Протокол завершения** — ссылка на skill `finish-task` и требование отчёта.

Пропущенный блок «границы» — самая частая причина того, что агент правит чужой
слой; пропущенный «критерий готовности» — причина отчёта «сделано» без
доказательств.

## 4. Готовые промпты

Подставьте своё в `<...>`. Формулировки намеренно избыточны — лишний абзац
дешевле переделанной задачи.

### Планировщик (сначала, если слоёв больше одного)

```text
Задача: <что нужно получить>.
Прочитай CLAUDE.md и docs/seo-requirements.md.
Разложи на назначения агентам-реализаторам: кто, какие файлы, что именно делает.
Укажи порядок (что параллельно, что последовательно и почему), нужна ли изоляция
в worktree, какие контролёры обязательны, и что принципиально требует решения
человека. Код не пиши.
```

### Реализатор Astro

```text
Цель: <что должно работать на странице или роуте>.
Границы: правишь только apps/web/. За её пределами — чтение.
Контекст: CLAUDE.md (разделы «Рендеринг», «Изображения», «Sitemap и robots»),
docs/seo-requirements.md п. <N>. Отчёт предыдущего агента: <вставить целиком>.
Порядок: сними базовый замер `pnpm test:seo` ДО правки; тест первым (TDD) в
tests/unit/; реализация; `pnpm verify` целиком; `pnpm test:seo` ПОСЛЕ, дельта в отчёт.
Инварианты: контент и первые изображения в HTML без JS; ровно один h1;
абсолютный self-canonical; навигация только <a href>; пагинация с постоянными URL.
Приёмочные spec-файлы в tests/seo/ сам не пиши — их владелец seo-auditor.
Перед завершением: вердикты seo-auditor, url-guard (если тронуты URL, canonical,
sitemap, редиректы), perf-guard (если тронуты шаблоны или вывод изображений), reviewer.
Заверши по skill finish-task, отчёт по шаблону.
```

### Реализатор Payload

```text
Цель: <что должно быть в модели данных или в правах>.
Границы: правишь только apps/cms/. За её пределами — чтение.
Контекст: CLAUDE.md (разделы «Модель данных», «Внешнее управление»),
docs/seo-requirements.md п. <N>.
Порядок: тест первым (TDD), обязательно на хуки и на access control; реализация;
`pnpm generate:types` после правки коллекций и использование сгенерированных типов;
`pnpm test:seo` до и после (sitemap и индексация зависят от модели);
`pnpm verify` целиком.
Инварианты: новая запись только в draft с noindex; published и index/noindex —
только роль admin; slug неизменяем после первой публикации, смена URL только
вместе с записью в redirects; seo-history фиксирует автора.
Каждое «ai-editor не может» подтверди тестом на access control.
Перед завершением: вердикты seo-auditor, url-guard, reviewer.
Заверши по skill finish-task, отчёт по шаблону.
```

### Реализатор изображений

```text
Цель: <что должен делать пайплайн>.
Границы: правишь только packages/images/. За её пределами — чтение.
Контекст: CLAUDE.md, раздел «Изображения».
Порядок: тест первым (TDD); для pHash — тест на устойчивость (одинаковые
изображения в разных форматах и размерах дают близкие хеши); реализация;
`pnpm verify` целиком.
Инварианты: AVIF + WebP + резервный JPEG; оригиналы отдельно от оптимизированных;
каждый вариант отдаёт известные width и height; имя файла на транслите, URL файла
постоянный; дедупликация предупреждает редактора, но не удаляет автоматически.
Перед завершением: reviewer; perf-guard, если менялись размеры или форматы вывода.
Заверши по skill finish-task, отчёт по шаблону.
```

### Владелец общего ядра

```text
Цель: <какая утилита или правило нужны в packages/shared>.
Границы: правишь только packages/shared/ и тесты в tests/unit/. Чужие вызовы не правишь.
Контекст: CLAUDE.md, раздел «Правила URL — нарушать запрещено».
Порядок: тест первым (TDD) с таблицей случаев для транслитерации (кириллица, ё,
ъ и ь, дефисы, двойные пробелы, цифры, латиница, пунктуация) и проверкой
идемпотентности slug(slug(x)) === slug(x); реализация; `pnpm verify` целиком.
Если правка меняет или удаляет существующий экспорт — найди всех потребителей
по монорепо и перечисли их в отчёте; правку у них делают владельцы слоёв.
Если правка может задеть уже существующие URL — напиши это первой строкой отчёта.
Перед завершением: вердикты url-guard и reviewer.
Заверши по skill finish-task, отчёт по шаблону.
```

### Редактор контента

```text
Цель: <какие страницы или карточки наполнить>.
Границы: содержание записей и docs/content/. Код в apps/ и packages/ не правишь.
Контекст: CLAUDE.md (разделы «Модель данных», «Правила индексации»),
docs/seo-requirements.md п. <N>.
Что заполнить: title, h1, description, вводный текст, alt, подписи, привязку
карточек к подборкам, внутренние ссылки.
Требования: title/H1/description уникальны по каталогу; никаких шаблонных текстов
с заменой пары слов; alt — естественное описание, не перечень ключей.
Граница: доводишь до статуса review и останавливаешься. published и index,follow —
только человек.
В отчёте обязательны разделы «Статусы контента» (что в draft, что в review,
published — «нет») и «Требует решения человека» с кандидатами на публикацию и
указанием, какие условия п. 5.1 выполнены, а какие нет.
Заверши по skill finish-task.
```

### Контролёры (вызываются в конце, можно одним сообщением)

```text
url-guard:
Проверь текущий диф на правила URL, canonical, редиректы и состав sitemap.
Верни вердикт по своему формату. Код не правь.

seo-auditor:
Прогони pnpm test:seo, сверь диф с чек-листом п. 22 и условиями п. 5.1.
Статус SKIPPED переноси дословно и не выдавай за PASS. Верни вердикт.

perf-guard:
Проверь диф на бюджеты производительности и на сдвиг макета (width и height,
контейнеры рекламы, lazy на LCP-изображении, порядок CSS и JS). Верни вердикт.

reviewer:
Отревьюй диф против запретов п. 23 и соглашений по коду. Одна строка на находку
с severity, затем итог PASS или FAIL. Код не правь.
```

## 5. Параллельность

Правило одно: **разные папки — можно одновременно, одна папка — нельзя.**
Независимые вызовы отправляйте одним сообщением с несколькими Agent tool —
тогда они действительно идут параллельно.

```text
Одним сообщением (независимы):
  payload-cms      -> apps/cms/src/collections/cards.ts
  images-pipeline  -> packages/images/src/phash.ts
  content-editor   -> docs/content/

Последовательно (есть зависимость):
  shared-core (транслитерация)     -> payload-cms (хук slug), astro-web (роуты)
  payload-cms (коллекция + types)  -> astro-web (шаблон по типам)
```

Контролёры запускаются после реализаторов, но между собой — параллельно: они
только читают.

### Когда нужен worktree

`isolation: "worktree"` — если два реализатора обязаны править один пакет.
Контролёрам worktree **не давайте**: им нужен реальный рабочий каталог с текущим
дифом, иначе они отревьюют пустоту и вернут PASS.

## 6. Приёмка работы агента

Отчёт без этих доказательств принимать нельзя.

| Проверка | Что должно быть в отчёте |
|---|---|
| `pnpm verify` | зелёный целиком, с выводом |
| `pnpm test:seo` до и после | дословный статус: `PASSED`, `FAILED` или `SKIPPED (<причина>)` |
| Вердикты контролёров | по формату каждого, включая `НЕ ПРОВЕРЕНО` там, где сайт не поднят |
| Статусы контента | что в `draft`, что в `review`; `published` — всегда «нет» |
| Требует решения человека | список, а не «ничего» по умолчанию |
| Не сделано | список, а не пустой раздел |

`SEO_ACCEPTANCE: SKIPPED` — **не** прохождение. Он существует, чтобы `verify` был
зелёным на скелете, пока сайт не поднят. Принять `SKIPPED` за `PASSED` — снять
страховку с приоритетного требования проекта.

FAIL любого контролёра блокирует завершение при зелёном `verify`. Находка идёт
владельцу слоя, после исправления проверки прогоняются заново — целиком, а не
только упавшая.

## 7. Чего не сделает ни один агент

Реализовано в серверных хуках и access control Payload, поэтому действует и через
API — не только в инструкциях:

- перевод в `published`;
- переключение `index/noindex`, открытие в `index,follow`;
- смена slug после первой публикации;
- создание и правка редиректов (роль `ai-editor`);
- ручная правка robots-директив и sitemap (роль `ai-editor`);
- массовое создание URL до готовности контента;
- публикация результата нейросетевой генерации без ручной модерации.

Это не перестраховка, а требование ТЗ (п. 7.1, п. 23). Агент доводит контент до
`review`; решение о публикации принимает человек.

## 8. Автоматические напоминания

`.claude/settings.json` подключает два хука. Оба только напоминают — блокирует
протокол, а не автоматика.

| Хук | Когда | Что делает |
|---|---|---|
| `seo-touch-reminder.mjs` | после `Write` и `Edit` | если файл в зоне риска (шаблоны, middleware, sitemap и robots, коллекции, общий контракт, пайплайн изображений) — напоминает, каких контролёров вызвать |
| `finish-reminder.mjs` | при остановке | печатает чек-лист протокола завершения |

## 9. Команды

```bash
pnpm install                # первая установка
pnpm verify                 # check + test + test:seo — перед завершением ЛЮБОЙ задачи
pnpm check                  # tsc -b + eslint
pnpm test                   # Vitest
pnpm test:seo               # приёмка SEO через шлюз
BASE_URL=http://localhost:4321 pnpm test:seo   # приёмка против поднятого сайта
pnpm generate:types         # типы Payload из коллекций (после apps/cms)
pnpm dev                    # dev-серверы web + cms (после установки приложений)
```

# Этап 0 — реестр входных решений

Документ фиксирует входные решения человека, без которых часть задач плана не может быть выполнена без домысливания. Решений за человека не содержит: то, что не отмечено как утверждённое в разделе 8, остаётся открытым.

**Источники:** `docs/plan-etapov.md` (разделы 0, 1, 9, 11, 12), `docs/tz-site-admin.md` (§1–16), `docs/seo-requirements.md`, `CLAUDE.md`, `agent_readme.md`.

**Правило, действующее до заполнения `docs/seo-requirements.md`:** требование есть в `CLAUDE.md` — выполняем по `CLAUDE.md`; требование упомянуто только номером пункта, а формулировки нет — это вопрос человеку, а не повод для догадки.

**Легенда срочности:**

| Метка | Значение |
|---|---|
| `BLOCKER-NOW` | без ответа нельзя законно начать этап 1 (Э1-01 / Э1-02) |
| `BLOCKER-LATER` | нужен к конкретной задаче/этапу, старт этапа 1 не блокирует |
| `NON-BLOCKING` | параметр: выносится в конфиг/env и покрывается тестом, значение утверждается позже |

**Легенда цены поздней смены:** `необратимо` — откат невозможен без потери индексации или удаления страниц; `дорого` — откат возможен, но требует 301, переиндексации или перегенерации файлов; `дёшево` — правка в коде/конфиге без внешних последствий.

2. **Что блокирует:** Э1-08 — только в части точности формулировок условий `index,follow` (сама задача стартует по выжимке `CLAUDE.md`, см. п. 4; блокирующей зависимости в плане у неё нет), Э3-13 и вето V10 (ТЗ §16), Э4-07 (чек-лист приёмки, ТЗ §13, §14.2), Э5-06 и Э6-02 (формулировки запретов, ТЗ §16), вердикты `seo-auditor` и `reviewer` на всех этапах.

## 2. Домен, инфраструктура, хранилище

### Ч-02. Домен, канонический хост, протокол — ЧАСТИЧНО ЗАКРЫТО

1. **Что решено человеком:** значение хоста не выбрано и агентом не выбирается; человек выбрал вариант «пока параметр в env» (см. раздел 8) — абсолютный URL собирается **только** из env-параметра `SITE_URL` через единственный хелпер в `packages/shared`. В продуктовом коде хост не хардкодится: ни дефолта, ни фолбэка. Синтетическое значение хоста в фикстуре юнит-теста допустимо и необходимо — им проверяется сама сборка URL. Пустой `SITE_URL` — ошибка сборки, а не повод подставить значение по умолчанию; плейсхолдер вместо ошибки не допускается ни в `.env.example`, ни в коде.
2. **Что остаётся открытым:** сам домен, вариант `www`/без `www`, протокол. Догадка запрещена: ни ТЗ, ни `CLAUDE.md` их не задают.
3. **Что блокирует до ответа:** Э4-03 (`robots.txt` с абсолютной ссылкой на sitemap), Э4-04 (sitemap), Э7-01 (production/staging) — то есть всё, где значение уходит наружу. Э1-01 и Э3-01 разблокированы параметризацией.
4. **Срочность:** `BLOCKER-LATER` (была `BLOCKER-NOW`, понижена параметризацией).
5. **Тестируемые без знания значения инварианты:** canonical абсолютный, ровно один хост на весь сайт, завершающий слеш, отсутствие относительных canonical.
6. **Цена поздней смены:** до первой публикации — дёшево; после индексации — необратимо/дорого (301 всего сайта и переиндексация).

### Ч-03. S3-провайдер, регион, бакеты/префиксы, CDN-домен изображений

1. **Что решить:** провайдер, регион, имена бакетов/префиксов раздельно для оригиналов и производных, домен CDN.
2. **Что блокирует:** Э2-04 (адаптер хранилища), Э2-05 (хук загрузки), Э2-06 (замена изображения), Э7-04 (CDN). Пункты: ТЗ §6.1, §6.7, §11, §12.
3. **Срочность:** `BLOCKER-LATER` — к Э2-04; Э2-01, Э2-02, Э2-03 стартуют без него.
4. **Рекомендуемый вариант:** догадка запрещена. Структурная часть уже нормирована ТЗ §6.1/§6.7 и §11: оригиналы — в отдельном пространстве, недоступном по угадываемым публичным URL; производные — публично, с immutable-кешированием.
5. **Параметризация:** снимается. `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET_ORIGINALS`, `S3_BUCKET_DERIVATIVES` (или `S3_PREFIX_*`), `IMAGES_CDN_ORIGIN` в `.env`/`.env.example`; тест проверяет разделение пространств и заголовки кеширования, а не значения.
6. **Цена поздней смены:** до публикации — дёшево; после — дорого/необратимо: смена CDN-домена меняет URL производных, а ТЗ §6.3 требует постоянного URL файла.

### Ч-13. Хостинг production, параметры PostgreSQL, доступы, провайдер 2FA

1. **Что решить:** площадка production с приемлемым TTFB из РФ/СНГ, параметры и доступы PostgreSQL (локально, staging, production), способ выдачи доступов, механизм 2FA.
2. **Что блокирует:** Э1-02 (bootstrap Payload), Э7-01 (окружения), Э7-03 (2FA), Э7-04 (TTFB ≤ 0,8 с). Пункты: ТЗ §11, §12, §10.
3. **Срочность:** расщепляется. Локальная БД для разработки — `BLOCKER-NOW` (без строки подключения Э1-02 не стартует). Production-хостинг, доступы, 2FA — `BLOCKER-LATER` (этап 7).
4. **Рекомендуемый вариант:** догадка запрещена по провайдеру, доступам и 2FA. Норма ТЗ §11/§12 (HTTPS-only админка, секреты в env, 2FA для администраторов, три окружения) подтверждения не требует.
5. **Параметризация:** снимается для старта. `DATABASE_URL`, `PAYLOAD_SECRET`, `PAYLOAD_ADMIN_PATH` в `.env`/`.env.example`; локальная разработка — на локальном PostgreSQL.
6. **Цена поздней смены:** дорого, но обратимо; необратимого следа в индексе не оставляет, если домен (Ч-02) не меняется.

### Ч-18. Домен staging и способ его закрытия

1. **Что решить:** адрес staging и конкретный механизм закрытия (HTTP-авторизация — каким слоем).
2. **Что блокирует:** Э7-01, Э7-02 (CI гоняет `pnpm test:seo` против стенда), вето V13. Пункты: ТЗ §12, §14.2.
3. **Срочность:** `BLOCKER-LATER` — к этапу 7. Сдвигается раньше, если Э4-07 решено гонять против общего стенда, а не локального `BASE_URL`.
4. **Рекомендуемый вариант:** догадка запрещена по домену. Способ закрытия нормирован ТЗ §12 — HTTP-авторизация + `noindex`.
5. **Параметризация:** снимается частично. `STAGING_BASIC_AUTH_USER/PASSWORD`, признак окружения (`ENVIRONMENT=staging`) и производная политика `noindex`; spec V13 проверяет, что не-production окружение анонимно недоступно, отдаёт `noindex` и не ссылается на production абсолютными URL.
6. **Цена поздней смены:** дорого — утечка staging в индекс даёт дубль всего сайта.

## 3. Структура и URL

### Ч-04. Структура разделов и иерархия подборок — В РАБОТЕ

1. **Что решено о процессе:** черновик структуры готовит агент, утверждает человек. Черновик — `docs/etap-0-struktura-url.md`, статус «предложение, не утверждено».

Открытые подвопросы вынесены в раздел 6 черновика: Ч-04-1 (частотность), Ч-04-2 (ветка «Адресаты»), Ч-04-3 (ветка «Стили»), Ч-04-4 (спорные slug), Ч-04-5 (форма таксономии), Ч-04-6 (порог перекрытия), Ч-04-7 (порядок сегментов), **Ч-04-8 (достижимость карточек за первой страницей списка — блокирует критерий «нет страниц-сирот» и должен быть закрыт до Э1-05)**.

4. **Срочность:** `BLOCKER-LATER`, но срок жёсткий — до старта Э1-05, то есть в первые дни этапа 1.

### Ч-05. Вариант пагинации — ЗАКРЫТО

1. **Что решено человеком:** `/page/N/` — сегментом пути, один вариант на весь сайт (выбор из предложенных вариантов, см. раздел 8). Вариант `?page=N` человеком не выбран; агент при подготовке вариантов отметил, что он потребовал бы явного исключения из правила «URL без параметров». Первая страница любого списка живёт по базовому URL, `/page/1/` не создаётся.
2. **Что сделано:** решение внесено в `CLAUDE.md`, раздел «Правила URL».
3. **Что затрагивает:** Э3-07 (шаблон пагинации), Э4-04 (исключение из sitemap), Э4-06 (матрица статусов), Э4-07 (spec), вето V6.
4. **Цена поздней смены:** дёшево до появления контента; дорого после — каждый существующий URL пагинации потребует одиночного 301.

### Ч-20. Подтвердить, что `/pozdravleniya/` не создаётся

1. **Что решить:** формально подтвердить отказ от раздела текстов поздравлений в текущем объёме.
2. **Что блокирует:** Э3-08 (каталоги разделов), навигацию, состав sitemap (Э4-04), Э4-08. Пункты: ТЗ §15, §16; п. 23 SEO ТЗ.
3. **Срочность:** `NON-BLOCKING` — по умолчанию раздел не создаётся; ответ нужен, только если человек решит иначе.
4. **Рекомендуемый вариант:** выводится из источников — ТЗ §15 относит раздел к этапу 2 развития, §16 и п. 23 запрещают создание URL до готовности контента. По умолчанию: роут не создаётся, в навигацию не добавляется, в sitemap не попадает.
5. **Цена поздней смены:** отказ сейчас — дёшево; преждевременное создание — необратимо.

### Ч-22. Форма директив `Disallow` в robots.txt и путь админки (новый, заведён 2026-08-19)

1. **Что решить:** в какой форме записывать директивы `Disallow` для служебных путей: со слешем (`/search/`, `/admin/`, …), без слеша (`/search`, `/admin`, …) или обеими строками сразу.
2. **В чём расхождение:** ТЗ §7.4 перечисляет закрываемые ПУТИ со слешем, но синтаксиса директив не задаёт; форма со слешем в `CLAUDE.md` — трактовка этого перечня, а не цитата. Технически `Disallow: /admin/` не покрывает голый `/admin` — а именно этот URL краулер запрашивает первым, и он же отдаёт страницу входа в админку. Форма без слеша покрывает оба варианта, но, будучи префиксным правилом, закроет и будущие контентные пути, начинающиеся с тех же букв (`Disallow: /admin` заденет `/administrativnye-.../`). Третий вариант — две строки, `/admin` и `/admin/`, — технически точен, но многословен. Агент такое расхождение не сглаживает: до ответа человека действует форма из ТЗ, расхождение помечено здесь и в `CLAUDE.md`.
3. **Что блокирует:** Э4-03 (`robots.txt`). Пункты: ТЗ §7.4. Закрытие staging (Ч-18, вето V13) от этого вопроса не зависит — там HTTP-авторизация, а не robots.
4. **Срочность:** `BLOCKER-LATER` — к Э4-03.
5. **Смежное:** путь админки параметризован (`PAYLOAD_ADMIN_PATH`), поэтому в `robots.txt` он берётся из env, а не хардкодится: при нестандартном значении директива из ТЗ не закроет реальный путь, а при публикации нестандартного пути в `robots.txt` он становится общеизвестным. Второе — тоже вопрос человеку: закрывать админку директивой (тогда нестандартный путь становится общеизвестным) или не публиковать её в robots.txt вовсе, полагаясь на HTTP-авторизацию и отсутствие ссылок.
6. **Цена поздней смены:** дёшево — `robots.txt` перегенерируется; но незакрытый `/admin` в индексе чистится вручную.

### Ч-23. Индексируемость служебных информационных страниц (новый, заведён 2026-08-19)

1. **Что решить:** должны ли `/o-proekte/`, `/usloviya/`, `/kontakty/` оставаться `noindex` и вне sitemap, или для них делается именованное исключение с открытием в `index,follow`.
2. **В чём расхождение:** `CLAUDE.md` и ТЗ §7.2 требуют «всегда `noindex` + вне sitemap» для служебных страниц, не разделяя технические (поиск, кабинет, превью) и информационные (о проекте, условия, контакты). Черновик структуры сначала ввёл для вторых собственный тип «служебно-информационная» с возможностью открыть в индекс — такого типа в источниках нет, и агент отменил это сам: страницы приведены к правилу, вопрос вынесен человеку.
3. **На что влияет:** Э3-11 (служебные страницы), Э4-04 (состав sitemap), Э4-08 (достижимость). Блокирующей зависимостью не является — действует значение по умолчанию. Пункты: ТЗ §5.6, §7.2.
4. **Срочность:** `NON-BLOCKING` — как и Ч-20, вопрос имеет действующее значение по умолчанию (общее правило `noindex` + вне sitemap), поэтому Э3-11 не блокирует. Ответ нужен, только если человек решит открыть эти страницы в индекс.
5. **Что учесть при ответе:** страница «Условия использования» адресуется из JSON-LD (`acquireLicensePage`) — ссылка работает и на неиндексируемой странице, поэтому техническим доводом за индексацию это не является. Довод против `noindex`: страницы такого типа обычно формируют доверие и в выдаче по брендовым запросам полезны.
6. **Цена поздней смены:** дёшево в обе стороны — страницы малочисленные, URL не меняются.

### Ч-21. Слеш для файлов скачивания и производных изображений

1. **Что решить:** подтвердить, что единое правило слеша применяется только к маршрутам страниц, а URL файлов слешем не заканчиваются и middleware их не редиректит.

4. **Суть расхождения:** `CLAUDE.md` приводит образец `otkrytka-mame-na-8-marta-s-tulpanami.webp`, а таблица (правило `ю → yu`, практика BGN/PCGN) даёт `otkrytka-mame-na-8-marta-s-tyulpanami.webp`. ### Ч-25. Транслитерация письменностей, для которых таблица не задана

1. **Что решить:** как обрабатывать литеры письменностей, для которых таблица транслитерации не задана: `і`, `ї`, `є`, `ґ` (украинский), `ў` (белорусский), `ә`, `ү`, `қ`, `ң`, `ө`, `һ` (казахский), `ı`, `ə`, `ç`, `ş`, `ğ` (азербайджанский), а также армянский, грузинский и греческий алфавиты. Формулировка расширена 2026-08-20 по находке U1 контролёра `url-guard`: изначально вопрос был только про кириллицу, но привязка к письменности оставляла ту же дыру для остальных — Азербайджан, Армения и Грузия входят в заявленную географию (ТЗ §16).
2. **Что блокирует:** slug любой записи с такой литерой. Пункты: `CLAUDE.md` раздел «Правила URL», ТЗ §7.5, §16 (география — Россия и СНГ).
3. **Срочность:** `BLOCKER-LATER` — до первой публикации; но чем раньше, тем лучше: slug заполняет AI-редактор, а неверный slug выглядит правдоподобно.
4. **Почему это вопрос, а не догадка:** правил нет ни в `CLAUDE.md`, ни в SEO ТЗ. Найдено контролёром `reviewer` на дифе этапа 2: `Київ` давал `ki-v`, `Гүлдер` — `g-lder`, `ў садзе` — `sadze`. После первой правки (отказ на кириллице) `url-guard` нашёл остаток того же класса: `Bakı → bak`, `Ənvər açıq → nv-r-ac-q`, `Բարև открытки → otkrytki`, `გილოცავ открытки → otkrytki`. Все проходили валидатор и выглядели правдоподобно.
5. **Текущее поведение (не решение):** любая литера, которая после таблицы транслитерации и снятия диакритики не дала ни одного допустимого символа, обрывает `slugify` целиком — результат пустой, то есть явно непригодный: валидатор его отклоняет, запись без slug не заводится. Отказ ВСЕЙ строки, а не пропуск литеры: иначе «Открытки для Наталії» дало бы `otkrytki-dlya-natali`, правдоподобный slug другого слова. Латиница с диакритикой при этом по-прежнему теряет диакритику (`Café → cafe`), а не отказывает. Третье правило, того же происхождения: **одиночная комбинирующая метка отбрасывается**, а не становится дефисом, — иначе `İstanbul` (U+0130 после понижения регистра распадается на `i` + U+0307, составной строчной формы у него не существует) дал бы `i-stanbul`, а «по́здравления» со знаком ударения — `po-zdravleniya`. Отказ здесь неуместен: базовая литера допустимый символ дала, а строчная форма `İ` в турецком и азербайджанском — именно `i`. Побочно это перестало рвать русский текст со знаком ударения. Все три правила — защита от тихой ошибки, а не выбранная норма.
6. **Варианты:** (а) внести таблицы нужных письменностей в `packages/shared` — тогда заголовки на этих языках дают корректный slug; (б) оставить отказ и запрещать такие заголовки валидацией в CMS (редактор задаёт slug вручную латиницей).
7. **Цена поздней смены:** до публикации — дёшево; после — смена URL опубликованных записей, то есть 301 на каждую.

3. **Срочность:** `BLOCKER-LATER` — до первой публикации.
4. **Почему это вопрос:** «короткое описательное» нормой не является, числа нет ни в одном документе.
5. **Текущее поведение (не решение):** `DEFAULT_SLUG_MAX_LENGTH = 80` в `packages/shared` и `DEFAULT_IMAGE_NAME_MAX_LENGTH = 68` в `packages/images` — параметры с документированными дефолтами, помеченными в коде как «не решение человека». 68 выбрано так, чтобы сегмент с суффиксом `-1920.webp` оставался внутри 80.
6. **Цена поздней смены:** уменьшение лимита после публикации меняет URL уже опубликованных записей и файлов; увеличение — безопасно.

### Ч-27. Slug из одних цифр

1. **Что решить:** отклонять ли slug, состоящий только из цифр (`2027`, `8`).
2. **Что блокирует:** ничего; риск в том, что правило «год не добавляется в URL ежегодных праздников» формально не нарушено, а фактически обойдено. Пункты: `CLAUDE.md` раздел «Правила URL».
3. **Срочность:** `NON-BLOCKING`, но до заведения первой подборки.
4. **Почему это вопрос:** запрещён год и зависимость URL от ID, но формального запрета на числовой slug нет, а по форме отличить `2027` от «8 Марта без второго слова» невозможно.
5. **Текущее поведение (не решение):** валидатор такой slug принимает. Запрет года в URL ежегодного праздника в коде пока не существует нигде — `slugify` пропустит `Новый год 2027` как `novyy-god-2027`; guard относится к остатку Э1-01 и к хуку Э1-09.
6. **Цена поздней смены:** после публикации — 301 на каждую затронутую запись.

### Ч-28. Механизм версионирования производных при замене изображения

1. **Что решить:** из чего берётся сегмент `revision` в ключе производной.
2. **Что блокирует:** Э2-05, Э2-06. Пункты: ТЗ §6.7, §6.3, §11 (immutable-кеширование).
3. **Срочность:** `BLOCKER-LATER` — до Э2-06, обязательно до первой публикации.
4. **Почему это вопрос:** в ТЗ параметра нет дословно. Он появился при реализации Э2-02, потому что §6.7 («замена изображения даёт новые URL производных») несовместим с immutable-кешированием без версионирования: тот же путь после замены отдавал бы старую картинку из кеша.
5. **Текущее поведение (не решение):** `revision` — обязательный параметр без дефолта, валидируется как один сегмент slug; значение выдаёт вызывающий код (Э2-05).
6. **Требование контролёра `url-guard` (условие C2, не вариант на выбор):** `revision` обязана меняться ТОЛЬКО при замене байтов изображения. Выводить её из `updatedAt`, версии записи или счётчика сохранений нельзя — каждое сохранение переписало бы URL всех производных. Привязка к содержимому (хеш байтов или id нового оригинала) делает незаметную смену URL структурно невозможной.
7. **Цена поздней смены:** после публикации — смена URL всех производных.

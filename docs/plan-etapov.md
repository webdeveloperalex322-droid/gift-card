## 0. Проверенное состояние репозитория (на момент планирования)

Проверено чтением файлов, не со слов:

- `apps/web/` и `apps/cms/` — только `package.json` + `README.md`, каталоги `src/` пусты. Astro и Payload не установлены.
- `packages/shared/src/index.ts` — заглушка: `TRAILING_SLASH = true`, `CONTENT_STATUSES`, `NON_INDEXABLE_STATUSES`, `isIndexableStatus()`. Транслитерации и валидации URL нет.
- `packages/images/src/index.ts` — заглушка: `OUTPUT_FORMATS`, `FALLBACK_FORMAT`. sharp не установлен.
- `tests/unit/` — один `workspace.test.ts`; `tests/seo/` — только `README.md`, spec-файлов нет, Playwright не установлен.
- `scripts/seo-gate.mjs` возвращает `SEO_ACCEPTANCE: SKIPPED` при отсутствии spec-файлов или незаданном `BASE_URL`; `scripts/not-scaffolded.mjs` заглушает `dev`, `build`, `generate:types`.
- Корневой `package.json`: `verify = check && test && test:seo`. Ветка `main`, дерево чистое, один коммит.

Вывод: **кода приложения нет**, `pnpm verify` зелёный только потому, что SEO-приёмка пропускается. Всё планирование ниже исходит из «нулевого» состояния.

Замечание по документам: в `CLAUDE.md`, раздел «Структура репозитория», файл `docs/tz-site-admin.md` подписан как «Полное ТЗ — источник истины», тогда как преамбула того же `CLAUDE.md` и раздел 1 ТЗ отдают приоритет `docs/seo-requirements.md`. Расхождение формальное, но его должен снять человек (см. вопрос Ч-01a).

## 9. Порядок, параллелизм и критический путь

### Критический путь

```text
Ч-01/Ч-02/Ч-04 (человек)
  → Э1-01 (shared: slug, canonical)
  → Э1-02 (Payload bootstrap)
  → Э1-04/Э1-05 (cards, collections) → Э1-10 (generate:types)
  → Э1-06 → Э1-09 (redirects + неизменяемость slug)
  → Э3-02 (данные в web) → Э3-05/Э3-06 (карточка, подборка)
  → Э4-01 (canonical/robots) → Э4-02 (редиректы) → Э4-04 (sitemap)
  → Э3-13 + публикация эталона человеком
  → Э4-07 (SEO-тесты, PASSED)
  → Э7-02 (CI) → Э7-08 (приёмка)
```

Всё остальное подвешивается к этой линии и её не удлиняет.

### Что идёт параллельно

| Волна | Одновременно | Почему можно |
|---|---|---|
| В1 | Э1-01 (shared) · Э1-02 (cms) · Э2-01, Э2-03 (images) · Э3-01 (astro bootstrap) | разные пакеты, пересечений по файлам нет |
| В2 | Э1-04, Э1-05, Э1-06 | один пакет `apps/cms` → **worktree на каждую** или строгая последовательность |
| В3 | Э2-02 (images) · Э1-07…Э1-09 (cms) · Э3-03, Э3-04 (web-компоненты) | разные владельцы |
| В4 | Э3-05 · Э3-06 | оба в `apps/web/src/pages` — **worktree**, иначе последовательно |
| В5 | Э3-08…Э3-12 | независимые шаблоны, но общий layout — координировать правки layout одной задачей |
| В6 | Э5-01…Э5-03 (cms) · Э4-07 (tests/seo) | разные каталоги, разные агенты |
| В7 | Э6-01…Э6-04 (cms) · Э7-03 web-часть · Э7-04 | разные слои |

### Что строго последовательно

1. Э1-01 → всё, что строит URL (иначе правила slug разъедутся между cms и web).
2. Э1-06 → Э1-09 (нельзя требовать атомарного 301, пока некуда его записать).
3. Э1-04/Э1-05 → Э1-10 → Э3-02 (типы генерируются до шаблонов; ручное дублирование типов — находка `reviewer`).
4. Э4-01 → Э4-02 → Э4-04 → Э4-05.
5. Э2-01…Э2-03 → Э2-04 → Э2-05 → Э2-06.
6. Э3-13 + ручная публикация → Э4-07 (SEO-тестам нужны индексируемые страницы; создать их может только человек).
7. Э6-02 → Э6-05 (негативные тесты после того, как есть что запрещать).

### Изоляция (git worktree)

Нужна там, где два реализатора обязаны править один пакет:

- Э1-04 / Э1-05 / Э1-06 — все в `apps/cms/src/collections/`.
- Э3-05 / Э3-06 / Э3-07 — все в `apps/web/src/pages/`.
- Э1-01 (`payload-cms` правит `packages/shared`) и Э2-02 (`images-pipeline` читает оттуда транслитерацию) — если понадобится расширять экспорт `shared` одновременно.
- Э4-04 (`astro-web`, sitemap) и Э4-05 (`payload-cms`, триггер) — разные папки, но общий контракт; контракт фиксируется до старта обеих.

Контролёрам worktree не выдаётся: им нужен реальный рабочий каталог с текущим дифом.

### Документы и требования

- **Ч-01.** Полный текст пунктов SEO ТЗ: **5.1** (условия `index,follow`), **6.4** (директива для пагинации — на него ссылается §5.3 ТЗ, но в `docs/seo-requirements.md` он даже не перечислен среди недостающих), **7.1** (запрет автопубликации), **22** (чек-лист приёмки), **23** (критические запреты). До заполнения агенты работают по выжимке в `CLAUDE.md` и помечают расхождения.
- **Ч-01a.** Снять расхождение: `CLAUDE.md` в разделе «Структура репозитория» называет источником истины `docs/tz-site-admin.md`, а в преамбуле — `docs/seo-requirements.md`.
- **Ч-01b.** Расхождение по пагинации: `CLAUDE.md` требует всегда `noindex` + вне sitemap; ТЗ §5.3 допускает «`noindex,follow` либо вариант из SEO ТЗ п. 6.4». Какой вариант принят.

### Домен, инфраструктура, хранилище

- **Ч-02.** Домен, канонический хост (`www` или без), протокол. Без этого нельзя строить абсолютный canonical, sitemap и robots.
- **Ч-03.** S3-совместимый провайдер, регион, имена бакетов/префиксов для оригиналов и производных, CDN-домен для изображений.
- **Ч-13.** Хостинг production с учётом TTFB из РФ/СНГ, параметры PostgreSQL, доступы к окружениям, провайдер 2FA.
- **Ч-18.** Домен staging и способ его закрытия (HTTP-авторизация, конкретный механизм).

### Структура и URL

- **Ч-04.** Фактическая структура разделов первого уровня и иерархия подборок (праздник → адресат/стиль): полный список узлов с их slug. Это URL — после публикации они неизменны.
- **Ч-05.** Вариант пагинации: `?page=N` или `/page/N/` — один на весь сайт, и её robots-директива (см. Ч-01b).
- **Ч-20.** Подтвердить, что `/pozdravleniya/` **не создаётся** в текущем объёме (ТЗ §15 относит его к этапу 2 развития, §16 запрещает создание URL до готовности контента).
- **Ч-21.** Политика по URL с завершающим слешем для файлов скачивания и производных изображений (файлы слешем не заканчиваются — подтвердить, что правило слеша применяется только к страницам).

### Контент и публикация

- **Ч-06.** Состав эталонной выборки для приёмки (главная, раздел, праздничная посадочная, дочерняя подборка, карточка, пагинация, поиск, URL с параметрами, удалённая карточка, 404) и минимальный объём открыток в посадочной (`CLAUDE.md` даёт ориентир 20–40 для широкой темы — подтвердить для конкретных тем).
- **Ч-07.** Публикация (`review→published`) и открытие в `index,follow` — **всегда решение человека, на каждой странице**. Агент доводит до `review` и перечисляет кандидатов в разделе «Требует решения человека» своего отчёта.
- **Ч-19.** Тексты служебных страниц: «О проекте», «Условия использования», «Контакты».
- **Ч-17.** Данные для `Organization` JSON-LD: название, контакты, юридические реквизиты.
- **Ч-12.** Календарь праздников и окно готовности (ТЗ говорит «за 4–8 недель» — нужны конкретные даты и ответственные).
- **Ч-16.** Список пользователей и ответственных редакторов.

### Параметры, которые ТЗ задаёт примером, а не нормой

- **Ч-09.** Набор ширин для `srcset`: ТЗ пишет «например 320/640/960/1280/1920» — это пример. Нужен утверждённый набор.
- **Ч-08.** Порог pHash-похожести (в коде это параметр, значение задаёт человек).
- **Ч-14.** Числовые значения rate limit на API-ключ.
- **Ч-15.** Подтвердить регламент бэкапов: ежесуточно, ≥ 30 дней, и кто владеет процедурой восстановления.

### Юридическое и коммерческое

- **Ч-10.** Лицензия на изображения: значения `license`, `acquireLicensePage`, `creator`, `creditText`, `copyrightNotice`, а также формулировка указания на генерацию ИИ в соответствии с политиками Яндекса и Google. Агент не сочиняет юридические тексты.
- **Ч-11.** Рекламная сеть, форматы и точные размеры блоков (нужны для резервирования места и CLS < 0,1).

## 12. Риски порядка (где неверная последовательность даёт необратимый ущерб)

| Риск | В чём необратимость | Чем закрывается в плане |
|---|---|---|
| Первая публикация до готовности хука неизменяемости slug (Э1-09) | URL фиксируется навсегда с момента первой публикации; если хук ещё не работает, slug можно изменить без 301 и потерять индексацию | Э1-09 и V2 — до любой публикации, даже на staging |
| Публикация до middleware редиректов (Э4-02) | перенос страницы в этот период приводит к 404 на индексированном URL | Э4-02 обязателен до Э3-13/публикации |
| Sitemap до правил canonical (Э4-01 → Э4-04) | поисковые системы получают неканонические адреса; переиндексация занимает недели, часть URL склеивается не туда | жёсткая последовательность Э4-01 → Э4-02 → Э4-04, вето V7 |
| Массовое создание URL/записей до готовности контента | прямое нарушение §16 ТЗ и п. 23 SEO ТЗ; «тонкие» страницы попадают в индекс и тянут вниз весь домен | Э3-13 — ручная эталонная выборка, не генерация; V10; отказ от `/pozdravleniya/` (Ч-20) |
| Автопубликация результата генерации | нарушение §16; репутационный и поисковый ущерб, откатывается только удалением с 404/410 | Э1-08 (только `admin`), Э5-06 (`published` поштучно), Э6-02 (запрет для `ai-editor`), V11/V12 |
| Загрузка изображений до правил имён (Э2-02) и pHash (Э2-03) | переименование опубликованных файлов ломает индексацию изображений; дубли уже попали в индекс | Э2-02/Э2-03 до Э2-05; V3 |
| Замена изображения без правила «новые URL производных при неизменном URL карточки» (Э2-06) | либо застревает кеш CDN, либо теряется URL карточки | Э2-06, V3 |
| Шаблоны в `apps/web` до `pnpm generate:types` (Э1-10) | ручные дубли типов расходятся со схемой; правки коллекций перестают ловиться компилятором — находка `reviewer` уровня critical | Э1-10 строго до Э3-02 |
| Staging открыт индексации (Э7-01) | дубль всего сайта в индексе; чистится месяцами | Э7-01, V13 |
| SEO-тесты пишутся после того, как шаблоны признаны готовыми | регрессии обнаруживаются на проде; `SKIPPED` подменяет проверку | Э4-07 сразу после появления эталонного контента; V14; правило «`test:seo` до и после правки» |
| Повторные смены slug одной записи | цепочки редиректов A→B→C, запрещённые ТЗ | Э1-06 (схлопывание цепочек при создании), V2/V9 |
| Реклама подключается после замеров производительности | CLS и LCP уезжают уже на проде, где правка дороже | Э3-12 до Э7-04; замеры §10 делаются с рекламными контейнерами |

## 13. Риск для SEO — одной строкой

Задача трогает приоритетную зону целиком (URL, canonical, редиректы, sitemap, индексация, изображения): любая последовательность, в которой первая публикация или sitemap опережают Э1-09, Э4-01 и Э4-02, создаёт потерю URL, а она в этом проекте необратима.

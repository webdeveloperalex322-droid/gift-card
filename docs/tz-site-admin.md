# Техническое задание: сайт поздравительных открыток и админ-панель

Версия 1.0 · Август 2026

Настоящее ТЗ описывает разработку веб-сайта и админ-панели. Оно опирается на SEO ТЗ (`docs/seo-requirements.md`), которое является приложением №1 и источником истины по всем поисковым требованиям. При противоречии между документами приоритет у SEO ТЗ.

---

## 1. Общие сведения

**Продукт:** сайт с коллекцией поздравительных открыток. Изображения генерируются нейросетями и публикуются только после ручной модерации. Пользователи просматривают, скачивают и делятся открытками.

**География и поиск:** Россия и СНГ; продвижение в Яндексе и Google.

**Монетизация:** медийная и контекстная реклама. Органический поисковый трафик — основной канал привлечения, поэтому SEO-требования имеют приоритет над скоростью разработки.

**Масштаб:** на старте — сотни открыток и десятки подборок; целевой горизонт — десятки тысяч открыток, сотни посадочных страниц.

**Ожидаемый результат:** работающий сайт + админ-панель + API для внешнего управления + автоматизированный контур SEO-приёмки, развёрнутые на продакшн-инфраструктуре и прошедшие приёмочные тесты (раздел 14).

## 2. Термины

- **Карточка** — страница одной открытки с постоянным URL.
- **Подборка** — посадочная страница со списком открыток по теме (праздник, адресат, стиль).
- **Раздел** — узел верхнего уровня иерархии (`/otkrytki/`, `/pozdravleniya/`, `/podborki/`).
- **Статусная модель** — жизненный цикл записи: `draft` → `review` → `published`.
- **pHash** — перцептивный хеш изображения для поиска визуальных дублей.
- **Индексируемая страница** — страница со статусом 200, self-canonical и `index,follow`.

## 3. Стек и архитектура

| Слой | Технология |
|---|---|
| Фронтенд | Astro, гибридный режим (статика + SSR), TypeScript |
| CMS / API | Payload CMS (админка, REST/GraphQL API, access control, хуки) |
| БД | PostgreSQL |
| Хранилище файлов | S3-совместимое (оригиналы и оптимизированные копии раздельно) |
| Обработка изображений | sharp (AVIF/WebP/JPEG, размеры, pHash) |
| Тесты | Vitest (юнит), Playwright (SEO-приёмка) |
| Организация кода | Монорепозиторий (pnpm workspaces): `apps/web`, `apps/cms`, `packages/shared`, `packages/images`, `tests` |

Архитектурные инварианты:

1. Весь контент страницы (title, H1, canonical, хлебные крошки, текст, ссылки, первые изображения) присутствует в серверном HTML-ответе. Сайт полноценен при отключённом JavaScript.
2. Клиентский JS — только точечные острова Astro (кнопка скачивания, фильтры, шаринг). Ошибка JS не ломает отображение контента.
3. Бизнес-правила (неизменяемость URL, статусная модель, проверки дублей) реализуются в хуках Payload на сервере и действуют одинаково для админки и API.
4. Вся схема данных, SEO-логика и конфигурация живут в коде репозитория и проходят через git.

## 4. Роли пользователей

| Роль | Описание | Ключевые права |
|---|---|---|
| Посетитель | Анонимный пользователь сайта | Просмотр, скачивание, шаринг |
| Редактор | Сотрудник в админке | Создание/редактирование контента, перевод `draft`→`review` |
| Администратор | Владелец проекта | Всё, включая публикацию, `index/noindex`, редиректы, смену URL c 301, управление пользователями и API-ключами |
| `ai-editor` | Сервисный аккаунт (API-ключ) для AI-агента | См. раздел 11 |

Публикация (`review`→`published`) и открытие страницы в `index,follow` доступны только администратору. Это требование п. 7.1 и п. 23 SEO ТЗ и не подлежит ослаблению.

## 5. Публичная часть сайта: структура и страницы

### 5.1. Карта сайта

```text
/                                   Главная
/otkrytki/                          Каталог открыток (раздел)
/otkrytki/<slug>/                   Карточка открытки (единственный URL карточки)
/podborki/                          Каталог подборок
/podborki/<taxonomy-path>/          Подборка (иерархия: праздник → адресат/стиль)
/pozdravleniya/                     Тексты поздравлений (этап 2)
/search/                            Внутренний поиск (noindex)
/o-proekte/, /usloviya/, /kontakty/ Служебные страницы
```

Правила URL — по разделу 4 SEO ТЗ: нижний регистр, транслитерация, дефисы, завершающий слеш, без параметров и дат, без года у ежегодных праздников. URL неизменен после публикации.

### 5.2. Главная страница

- Заголовок и вводный блок с уникальным текстом.
- Блоки: актуальные праздничные подборки (сезонность), популярные разделы, свежие открытки.
- Сезонные блоки управляются из админки (дата начала/окончания показа).
- JSON-LD: `WebSite` + `Organization`.

### 5.3. Страница подборки

- H1, вводный текст (уникальный, содержательный), сетка карточек открыток.
- Превью карточки в сетке: изображение (lazy, кроме первого экрана), название, ссылка на карточку.
- Пагинация: обычные URL `?page=N` либо `/page/N/` (выбрать один вариант на весь сайт); страницы пагинации — canonical на себя, `noindex,follow` либо вариант из SEO ТЗ п. 6.4; вне sitemap.
- Ссылки на смежные подборки (перелинковка, п. 12 SEO ТЗ): вверх на родителя, вбок на 3–6 смежных, вниз на дочерние.
- Дата содержательного обновления.
- JSON-LD: `CollectionPage` + `ItemList` + `BreadcrumbList`.

### 5.4. Карточка открытки

- H1 (название открытки), изображение в максимальном качестве для просмотра, подпись/текст поздравления, описание.
- Кнопка «Скачать» (оригинальное качество; отдача файла — прямой URL, не создающий индексируемых страниц).
- Кнопки шаринга (WhatsApp, Telegram, VK, Одноклассники) — без загрузки внешних SDK, через share-URL.
- Атрибуты: повод, адресат, стиль; каждый — ссылка на соответствующую подборку.
- Блок «Похожие открытки» (6–12 шт.) — по общим подборкам и атрибутам.
- Хлебные крошки от главной по основной подборке.
- Открытка может входить в несколько подборок; у карточки всегда один URL и self-canonical.
- JSON-LD: `WebPage` + `ImageObject` (contentUrl, name, description, creator, creditText, copyrightNotice, license, acquireLicensePage) + `BreadcrumbList`. Указание на генерацию ИИ — в creditText/copyrightNotice в соответствии с политиками поисковых систем.

### 5.5. Внутренний поиск и фильтры

- Поиск по названию, подписи, атрибутам. Страница результатов: `noindex`, закрыта в robots.txt, вне sitemap.
- Фильтры на страницах подборок (стиль, формат, настроение) — работают на клиенте или через параметры, но не создают индексируемых URL: любые URL с параметрами фильтрации отдают canonical на чистую страницу подборки.
- Бесконечная лента запрещена.

### 5.6. Служебные страницы и ошибки

- Страница 404: отдаёт настоящий HTTP 404, содержит навигацию, поиск и ссылки на популярные подборки. Массовый редирект несуществующих URL на главную запрещён.
- Удалённая карточка: 404/410, при наличии близкой замены — одиночный 301.
- 503 + `Retry-After` при недоступности сервиса.
- Страницы «О проекте», «Условия использования» (лицензия на изображения), «Контакты».

### 5.7. Рекламные места

- Зарезервированные контейнеры фиксированных размеров (реклама не вызывает сдвигов макета, CLS < 0,1).
- Позиции: под первым экраном подборки, между рядами сетки (не чаще чем каждые 3 ряда), под изображением на карточке.
- Первый экран не занят рекламой полностью; рекламный код загружается отложенно и не блокирует LCP.

## 6. Изображения: пайплайн

1. Загрузка оригинала в админке (или через API) → сохранение оригинала в S3 (отдельный бакет/префикс, недоступный напрямую).
2. Автоматическая генерация производных: AVIF + WebP + JPEG-fallback в наборе ширин (например 320/640/960/1280/1920) для `srcset`.
3. Имя файла — короткое описательное на транслите (задаётся редактором или генерируется из названия), URL файла постоянный после публикации.
4. Расчёт pHash при загрузке; поиск визуально похожих среди опубликованных и находящихся в review; вывод похожих редактору до публикации.
5. Вывод на сайте: `<picture>`/`<img>` с обязательными `width`, `height`, `alt`, `srcset`/`sizes`. Первое крупное изображение страницы — без lazy, с `fetchpriority="high"`; остальные — `loading="lazy"`.
6. `alt` — естественное описание сцены; хранится в записи карточки; для декоративной графики — пустой alt.
7. Кеширование производных — длительное (immutable); замена изображения = новые файлы с новыми URL производных при неизменном URL карточки.

## 7. SEO-подсистема

Раздел фиксирует, что именно реализуется в коде. Полные требования — в SEO ТЗ.

### 7.1. Метаданные и canonical

- Поля title, meta description, H1, canonical, robots-директива редактируются раздельно для каждой страницы (карточки, подборки, разделы, служебные).
- Автогенерация по шаблону возможна как значение по умолчанию, с обязательной возможностью ручного переопределения.
- Canonical — всегда абсолютный; на индексируемых страницах — self.
- Ровно один H1 на страницу.

### 7.2. Индексация

- В `index,follow` страница переводится только вручную и только при выполнении условий п. 5.1 SEO ТЗ (спрос, интент, наполненность — ориентир 20–40 открыток для широкой темы, уникальные тексты, включение в навигацию).
- Всегда `noindex` и вне sitemap: поиск, фильтры, черновики, review, пагинация, служебные и технические страницы, автоматические теги.

### 7.3. Sitemap

- Sitemap-индекс `/sitemap.xml` → `sitemap-sections.xml`, `sitemap-cards-N.xml` (≤ 50 000 URL каждый), `sitemap-images-N.xml` (image-расширение).
- Включаются только абсолютные канонические URL, статус 200, `index`. Исключаются редиректы, 404, noindex, параметры.
- `lastmod` обновляется только при содержательном изменении.
- Автоматическая перегенерация по хукам публикации/переноса/удаления (инкрементально или фоновой задачей ≤ 15 минут).

### 7.4. robots.txt

Закрыты: `/search/`, `/account/`, `/admin/`, технические пути генерации/превью. Не блокируются CSS/JS/изображения. Указана абсолютная ссылка на sitemap-индекс.

### 7.5. Редиректы

- Управление 301-редиректами в админке: откуда, куда, дата, автор, комментарий.
- Middleware применяет редиректы до рендеринга; цепочки запрещены (при создании редиректа на URL, который сам редиректит, система схлопывает цепочку и предупреждает).
- Смена slug опубликованной записи возможна только атомарно с созданием 301 (одна операция в интерфейсе, доступна администратору).

### 7.6. Хлебные крошки

На всех страницах глубже главной; отражают иерархию; текущая страница — без ссылки; разметка `BreadcrumbList`.

## 8. Админ-панель: функциональные требования

### 8.1. Коллекции и поля

**cards (открытки):**

| Поле | Тип | Примечание |
|---|---|---|
| title, h1 | text | Раздельно; по умолчанию совпадают |
| slug | text | Неизменяем после публикации (хук) |
| image | upload | Запускает пайплайн раздела 6 |
| alt | text | Обязательно до перевода в review |
| caption | textarea | Подпись/текст поздравления |
| description, metaDescription | textarea | Раздельно |
| collections | relation m:n | Подборки; первая — основная (для крошек) |
| occasion, recipient, style, mood | select/relation | Атрибуты |
| status | select | draft / review / published |
| robots | select | index,follow / noindex,follow / noindex,nofollow |
| canonical | text | По умолчанию self; переопределение — только админ |
| pHash | text | Заполняется автоматически, readonly |
| publishedAt, updatedContentAt | date | updatedContentAt — только при содержательных правках |

**collections (подборки/разделы):** title, h1, slug (иерархический путь), вводный текст (rich text), metaDescription, canonical, robots, parent (иерархия), related (смежные, m:n), seasonal (даты показа на главной), status, ответственный редактор, updatedContentAt.

**redirects:** from, to, code (301/410), createdBy, comment. Валидация от цепочек и петель.

**seo-history:** запись при каждом изменении SEO-полей (title, h1, metaDescription, slug, canonical, robots, status): что, когда, кем (пользователь или сервисный аккаунт), старое → новое значение. Только чтение.

**users / api-keys:** роли по разделу 4.

### 8.2. Статусная модель и хуки

- Новая запись создаётся только в `draft`, `robots = noindex,follow`.
- `draft` → `review`: доступно редактору и `ai-editor`; валидация полноты (изображение, alt, title, подборки, caption) и прохождение проверок дублей.
- `review` → `published`: только администратор. Отдельным действием администратор включает `index,follow` (может оставаться noindex, если условия п. 5.1 SEO ТЗ не выполнены).
- `published` → правка: разрешена; slug заблокирован; смена статуса вниз (снятие с публикации) — только админ, с автоматическим предложением 301/404.
- Все правила — в серверных хуках Payload; интерфейс лишь отражает их.

### 8.3. Проверки качества (при сохранении и в дашборде)

1. **Дубли метатегов:** совпадение title или metaDescription с существующими записями → предупреждение со ссылками на конфликтующие страницы. Перевод в review при неразрешённом конфликте — с явным подтверждением.
2. **Визуальные дубли:** pHash-расстояние ниже порога → показ похожих изображений; перевод в review блокируется до решения редактора (подтвердить уникальность или отклонить).
3. **Полнота:** обязательные поля до review (см. 8.2).
4. **Внутренние ссылки:** фоновая проверка (ежесуточно): страницы-сироты (недостижимы за ≤ 4 перехода от главной), битые внутренние ссылки, страницы вне навигации. Результат — в дашборде.

### 8.4. Дашборд SEO-здоровья

Стартовый экран админки: количество страниц по статусам; предупреждения (дубли метатегов, визуальные дубли, сироты, битые ссылки, страницы в review); последние изменения из seo-history; статус последней генерации sitemap.

### 8.5. Массовые операции и выгрузка

- Выгрузка CSV: URL, тип страницы, статус записи, HTTP-статус, robots, canonical, title, наличие в sitemap, дата обновления.
- Массовое изменение статуса draft↔review для выбранных записей (published — только поштучно).
- Массовая привязка карточек к подборке.

### 8.6. Сезонное планирование

Календарь праздников (п. 20 SEO ТЗ): у подборки — целевая дата праздника и дата готовности (за 4–8 недель); дашборд показывает подборки, по которым дедлайн готовности приближается или сорван.

## 9. API и внешнее управление (AI-редактор)

- Используется штатный REST/GraphQL API Payload; отдельный API-слой не разрабатывается.
- Аутентификация сервисных клиентов — API-ключи; каждому ключу назначается роль.
- Роль `ai-editor`: создание/редактирование `draft`, загрузка изображений, метаданные, alt, привязка к подборкам, перелинковка, перевод `draft`→`review`. Запрещено: `published`, изменение robots/canonical опубликованных страниц, slug после публикации, редиректы, пользователи, ключи.
- Все хуки и валидации (раздел 8.2–8.3) выполняются для API-запросов без исключений.
- Rate limiting на API-ключ; логирование всех мутаций в seo-history с указанием ключа.
- (Этап 2) MCP-обёртка с задачными операциями: «создай черновик карточки», «прикрепи к подборкам», «проверь дубли», «переведи в review».

## 10. Производительность

Целевые метрики (75-й перцентиль, мобильные): LCP ≤ 2,5 с; INP < 200 мс; CLS < 0,1; TTFB ≤ 0,8 с; HTML без изображений ≤ 150 КБ.

Средства: статическая генерация стабильных страниц; кеширование SSR-ответов; Brotli; HTTP/2+; критический CSS инлайном, некритический — отложенно; JS-острова минимальны; длительное кеширование статики с контент-хешами; CDN для изображений; резервирование размеров изображений и рекламных контейнеров.

## 11. Безопасность

- Админка — только по HTTPS, за отдельным путём, с сильными паролями и 2FA для администраторов.
- Доступ к API — по ключам с ролями; ключи отзываемы; секреты — в переменных окружения, не в репозитории.
- Загрузка файлов: валидация типа и размера, обработка через sharp (пересборка изображения устраняет вредоносные полезные нагрузки), оригиналы недоступны по прямым угадываемым URL.
- Защита от CSRF/XSS средствами Payload и экранированием в шаблонах; заголовки CSP, X-Content-Type-Options, Referrer-Policy.
- Резервное копирование БД и S3 — ежесуточно, хранение ≥ 30 дней, документированная процедура восстановления.

## 12. Инфраструктура и деплой

- Окружения: local, staging, production. Staging закрыт от индексации (HTTP-авторизация + noindex).
- CI: на каждый PR — `tsc`, eslint, Vitest, Playwright SEO-тесты; деплой на production — только из main при зелёном CI.
- Хостинг production — с учётом аудитории РФ/СНГ (приемлемый TTFB из целевых регионов); CDN для статики и изображений.
- Мониторинг: доступность, ошибки 5xx, время ответа; логирование HTTP-статусов для контроля 404/301.
- Подключение и подтверждение сайта в Яндекс Вебмастере и Google Search Console; передача sitemap.

## 13. Тестирование

- **Юнит-тесты (Vitest):** транслитерация и валидация slug, логика canonical, генерация sitemap (фильтрация noindex/редиректов), pHash-сравнение, правила статусной модели, access control ролей.
- **SEO-приёмка (Playwright, `tests/seo/`):** кодирует чек-лист п. 22 SEO ТЗ на эталонной выборке страниц (главная, раздел, праздничная посадочная, дочерняя подборка, карточка, пагинация, поиск, URL с параметрами, удалённая карточка, 404): уникальность title/H1/description; единственный H1; абсолютный self-canonical; контент в HTML без JS; ссылки `<a href>`; корректные HTTP-статусы; чистота sitemap; атрибуты изображений; отсутствие индексируемых дублей от фильтров; отсутствие сирот.
- **API-тесты:** роль `ai-editor` не может выполнить запрещённые операции (публикация, смена slug, редиректы) — негативные сценарии обязательны.
- Тесты — часть CI; задача считается выполненной при зелёном `pnpm verify`.

## 14. Порядок приёмки

1. Все автотесты зелёные в CI на production-сборке.
2. Ручная проверка чек-листа п. 22 SEO ТЗ на staging.
3. Lighthouse/PageSpeed на эталонных страницах: целевые метрики раздела 10 достигнуты на мобильном профиле.
4. Проверка админ-сценариев: полный цикл draft → review → published → index; смена URL с 301; удаление с 404/301; выгрузка CSV; срабатывание предупреждений о дублях (метатеги и pHash).
5. Проверка API-сценариев роли `ai-editor` (позитивные и негативные).
6. Sitemap принят Яндекс Вебмастером и GSC без ошибок.

# tests/api — живые REST и GraphQL Payload

Запуск: `pnpm test` (входит в `pnpm verify`).
Только этот каталог: `pnpm exec vitest run tests/api`.
Один файл: `pnpm exec vitest run tests/api/access-negative.test.ts`.

## Что это

Права роли `ai-editor` записаны в access control и хуках Payload, а Payload сам
отдаёт REST и GraphQL. Юнит-тест на предикате отвечает на вопрос «правильно ли
записано правило», но не на вопрос «применяется ли оно» — на этапе 5 коллекция
`payload-jobs` осталась с дефолтными правами именно так: предикат был верен, его
просто не спрашивали. Поэтому здесь каждая граница доказывается ЗАПРОСОМ по тому
же пути, которым ходит внешний AI-редактор.

Транспорт — вариант A: обработчики маршрутов Next вызываются в процессе.
Импортируются файлы `apps/cms/src/app/(payload)/api/**/route.ts` — те же модули,
что обслуживают продакшн-запросы. `next start` не поднимается: сборка Next
заняла бы минуты на каждом `pnpm verify`. Цена выбора: маршрутизация Next
(rewrites `PAYLOAD_ADMIN_PATH`, заголовок `X-Robots-Tag`) этими тестами не
покрывается — она проверяется приёмкой `tests/seo/`.

## Требования к окружению

Нужен живой PostgreSQL из `DATABASE_URL` и созданная база
(`pnpm --filter @otkritka/cms run ensure-db`). При недоступной базе набор
ПАДАЕТ с внятным текстом и не пропускается: пропуск означал бы, что негативные
сценарии зелёные ровно тогда, когда ничего не проверяют, — та же подмена, что
выдача `SEO_ACCEPTANCE: SKIPPED` за `PASSED`.

Файлы этого каталога гоняются последовательно и в одном форке
(`poolOptions.forks.singleFork` у проекта `api` в корневом `vitest.config.ts`):
они делят одну базу и один экземпляр Payload. Длинные таймауты (`hookTimeout`,
`testTimeout`) заданы там же и только для этого проекта — чистым тестам они не
нужны, а общий таймаут в минуту прятал бы зависший юнит-тест.

## Как устроен негативный сценарий

Четыре шага, и меньше нельзя:

1. прочитать состояние в базе ДО операции — правами системы, а не ключом
   проверяемой роли;
2. выполнить запрещённую операцию через API;
3. прочитать состояние ПОСЛЕ и доказать, что оно не изменилось;
4. доказать, что операция ВООБЩЕ ВЫПОЛНИЛАСЬ, — иначе шаг 3 ничего не значит.

Код ответа сам по себе не доказывает ничего: отказ на уровне поля у Payload
молчаливый — поле вырезается из входных данных, на его место встаёт прежнее
значение, ответ 200. Поэтому каждый сценарий объявляет вид отказа параметром
`outcome`, а не комментарием:

- `silent` — правило живёт в access control поля. Требуется успешный ответ
  (`applied === true`) плюс совпадение снимков;
- `loud` — правило живёт в хуке `beforeOperation` или в access control операции.
  Требуется отказ с текстом.

Шаг 4 появился после разбора: три сценария были ложно-зелёными. Мутация GraphQL
без обязательного поля входного типа (`createRedirect` без `code`,
`createSeoHistory` без `operation`/`authorRole`/`changedAt`) и выборка
несуществующего поля (`updateSiteSetting { id }` — у типа глобала поля `id` нет)
отклоняются РАЗБОРОМ ЗАПРОСА: резолвер не выполняется, права никто не
спрашивает, а ответ по форме неотличим от отказа по правам. Такой сценарий
зелёный при полностью открытом access control.

Ловится это в гарнизоне, а не в тестах: `graphqlRaw` падает, если среди ошибок
есть хоть одна без `path` — признак того, что до резолвера дело не дошло
(у отказа из резолвера `path` есть всегда: `path: ["createRedirect"]`,
`extensions.name: "Forbidden"`). Сама эта проверка покрыта тестом
«набор ловит запрос, не дошедший до Payload» в `access-negative.test.ts`.

## Файлы

| Файл | Что доказывает |
|---|---|
| `harness.test.ts` | каркас работает: один сценарий проходит и через REST, и через GraphQL |
| `api-keys.test.ts` | Э6-01: выпуск, отзыв и чтение API-ключа — право администратора |
| `access-positive.test.ts` | Э6-02: путь агента до `review` целиком проходим |
| `access-negative.test.ts` | Э6-02: границы `ai-editor` — каждая через оба транспорта |

Гарнизон и фикстуры живут в `apps/cms/src/testing/` — у владельца проверяемого
кода; проверяет их типы `pnpm --filter @otkritka/cms run check` (он же
проверяет и этот каталог по `tests/api/tsconfig.json`).

Обратная сторона этого расположения: гарнизон лежит внутри `src` приложения и
разрешается из продуктового кода, а `readStored` и `removeContent` ходят с
`overrideAccess: true`, то есть в обход всего access control. Импорт из
продуктового кода запрещён правилом `no-restricted-imports` в `eslint.config.js`;
исключение из правила — только этот каталог.

## Что каталог за собой оставляет

Ничего в статусе `published`: фикстура снимает записи с публикации с решением
`404` и удаляет их вместе с журналом `seo-history`. Уборка не глушит ошибки и
отдельно проверяет состояние «после» (`assertRemoved`): проглоченная ошибка
уборки оставила бы в рабочей базе опубликованную запись или живой API-ключ, и ни
один тест бы не покраснел.

Единственное исключение — реестр `image-name-claims`: из него не удаляют ничего
и никогда (иначе освободившийся суффикс имени изменил бы путь файла у другой
записи), поэтому строки там накапливаются от прогона к прогону. Это свойство
модели, а не утечка.

# tests/seo — приёмочные SEO-тесты (контур обратной связи)

Владелец: агент `seo-auditor`. В коде приложений он только читает: найденное
нарушение называет, исправляет владелец слоя.

Тесты кодируют чек-лист приёмки из п. 22 ТЗ. Каждое требование — отдельный spec,
чтобы падение называло конкретное нарушение, а не «SEO сломано».

## Запуск

```bash
BASE_URL=http://127.0.0.1:4321 pnpm test:seo
```

Шлюз `scripts/seo-gate.mjs` печатает один из трёх статусов:

| Статус | Когда |
|---|---|
| `SEO_ACCEPTANCE: PASSED` | Playwright вернул 0 |
| `SEO_ACCEPTANCE: FAILED` | Playwright вернул не 0 |
| `SEO_ACCEPTANCE: SKIPPED` | нет spec-файлов или не задан `BASE_URL` |

**Пропуск не равен прохождению.** Статус переносится в отчёт о завершении задачи
дословно, вместе с причиной.

## Что поднимает сервер

Конфиг `playwright.config.ts` сам запускает `tests/seo/support/serve-built-web.mjs`:
тот собирает (`tsc -b packages/shared packages/images`, затем
`pnpm --filter @otkritka/web run build`) и поднимает **собранный** сервер
командой `pnpm --filter @otkritka/web run start`. Проект `tests/` он намеренно не
собирает: ошибка типов в чужом юнит-тесте не должна мешать приёмке сообщить о
состоянии сайта — типы всего монорепозитория проверяет `pnpm check`, который в
`pnpm verify` идёт раньше.

**Контракт с `apps/web`** (владелец — `astro-web`). Приёмка не знает, как
приложение поднимает сервер, и знать не должна: устройство слоя уже менялось
(standalone-адаптер → `mode: 'middleware'` со своим Node-сервером), и путь до
точки входа менялся вместе с ним. Нужны ровно два скрипта в
`apps/web/package.json`:

| Скрипт | Что обязан делать |
|---|---|
| `build` | собрать всё, что нужно серверу |
| `start` | поднять production-сервер, читая `HOST`, `PORT` и `SITE_URL` из окружения |

Пока `start` есть, приёмка переживает любую перестройку внутренностей. Если его
нет, используется прежний путь (импорт standalone-точки входа), и при неудаче
скрипт печатает, что именно нужно добавить, — а не «сервер не поднялся».

Против `astro dev` приёмку гонять нельзя: в dev-режиме при
`trailingSlash: 'never'` Astro вместо 301 показывает страницу-предупреждение со
статусом 404 (замерено на astro 7.2.4), и spec на одиночный 301 упал бы на верном
коде. Поэтому `reuseExistingServer` выключен — иначе приёмка могла бы молча
подхватить чужой dev-сервер на том же порту.

Переменные окружения приёмки:

| Переменная | Значение по умолчанию | Зачем |
|---|---|---|
| `BASE_URL` | нет, обязательна | адрес стенда: схема + хост + порт, без пути |
| `SEO_SERVER_PORT` | порт из `BASE_URL`, иначе `4321` | порт, на котором слушает поднимаемый сервер (нужен, если `BASE_URL` идёт через обратный прокси) |
| `SEO_SERVER_HOST` | `127.0.0.1` | интерфейс, на котором слушает поднимаемый сервер |
| `SEO_REUSE_SERVER` | не задана | `1` — приёмка идёт против уже поднятого сервера и своего не запускает |
| `SEO_MAINTENANCE_PORT` | порт стенда + 1 | порт ВТОРОГО сервера, который поднимает `maintenance-mode-503.spec.ts` с `MAINTENANCE_MODE=on`. Нужен, когда приёмку гоняют несколько агентов на одной машине |

### Второй сервер: режим обслуживания

Режим обслуживания — параметр окружения, читаемый процессом, который отвечает
(`apps/web/src/server/maintenance.ts`). Включить его у уже запущенного сервера
снаружи нечем — и это правильное устройство: выключатель, который можно дёрнуть
запросом, однажды будет дёрнут запросом. Поэтому `maintenance-mode-503.spec.ts`
поднимает свой процесс из `beforeAll` — тем же скриптом `start`, на порту
`SEO_MAINTENANCE_PORT`, и переиспользует уже собранный артефакт.

Второй записи `webServer` в конфиге нет намеренно: записи поднимаются
параллельно, а каждая по контракту начинает со СБОРКИ — две сборки писали бы в
один `dist`. Останов идёт по дереву процессов (`taskkill /T` на Windows): обёртка
`start` запускает сервер дочерним процессом, а Node на Windows не доставляет
сигналы, поэтому обычный `kill` оставил бы внука держать порт.

## `SITE_URL` и `BASE_URL` — один хост

`CLAUDE.md`, раздел «SEO-тесты»: на окружении приёмки они указывают на один хост,
иначе self-canonical укажет на другой хост и проверка canonical либо ложно
упадёт, либо будет ослаблена. **Ослаблять её запрещено.**

Как это решено здесь:

1. сервер, который поднимает сама приёмка, получает `SITE_URL` = origin
   `BASE_URL`. Окружение согласовано по построению, а не по договорённости;
2. согласованность всё равно проверяется на живом ответе —
   `environment-hosts-match.spec.ts` сравнивает origin self-canonical с origin
   `BASE_URL`. Этот spec нужен для режима `SEO_REUSE_SERVER=1` (там `SITE_URL`
   сервера приёмке неподконтролен) и ловит появление второго источника хоста в
   шаблонах (`Astro.site`, захардкоженный домен, фолбэк на `localhost`);
3. сравнение canonical идёт по абсолютному адресу целиком — схема, хост, порт,
   путь. Формы «оканчивается на путь» в specs нет.

Не проверяется машиной ровно одно: что значение `SITE_URL` продуктового
окружения совпадает с хостом, на котором сайт реально отдаётся. Локально это
непроверяемо в принципе. Чтобы приёмка шла против `http://otkritka.test` из
решения Ч-02, **нужно действие человека вне репозитория**: отобразить
`otkritka.test` на порт приложения (запись в `hosts` + обратный прокси на порт
из `SEO_SERVER_PORT`) и запускать `BASE_URL=http://otkritka.test pnpm test:seo`.
Пока этого нет, приёмка гоняется по адресу петли — и это указано в отчёте, а не
спрятано.

## Инвентарь страниц

Инвентарь разложен на три файла, и разделение содержательное:

| Файл | Что в нём |
|---|---|
| `support/declared-pages.ts` | ОБЪЯВЛЕННАЯ выборка: адреса и ожидаемые факты о каждой странице — директива робота (`expectedRobots`), состав изображений (`images`), вид структурированных данных (`structuredData`), наличие `<meta name="description">` (`description`), вид страницы из п. 22 (`sampleRole`) и условие появления (`appearsWhen`). Ни одного запроса, ни одного чтения окружения |
| `support/discovery.ts` | замер присутствия: какие из объявленных адресов стенд отдаёт в этом прогоне. Выполняется в `global-setup.ts` ДО загрузки spec-файлов, результат передаётся переменной окружения |
| `support/pages.ts` | то, что читают специи: `ACCEPTANCE_PAGES` (страницы, отвечающие 200) и `ABSENT_ACCEPTANCE_PAGES` (объявленные, но отсутствующие) |

Инвариантные specs (`single-h1`, `self-canonical-absolute`,
`robots-directive-present`, `unique-title-h1-description`,
`internal-links-are-anchors`, `server-rendered-without-js`,
`no-client-javascript`, `page-has-no-html-twin`, `image-attributes`,
`structured-data-matches-visible`, `canonical-ignores-query`,
`status-ignores-query`, `filtered-view-not-indexable`, `site-nav-present`,
`sidebar-present`, `category-menu-is-uniform`, `category-menu-links-are-live`,
`preloaded-fonts-are-served`, `served-text-has-no-tag-literals`,
`content-column-not-collapsed`, `indexable-has-description`) идут по
`ACCEPTANCE_PAGES`, поэтому новая страница добавляется ОДНОЙ записью в
`declared-pages.ts`, без правок в самих specs.

Виды «URL с параметрами», «404» и «удалённая карточка» своего адреса не имеют, и
их владельцы — отдельные specs либо честно объявленное «не покрыто»; сторожит это
`acceptance-sample-covers-checklist.spec.ts` (см. ниже).

Поля-ожидания существуют против ТАВТОЛОГИИ. Проверка «у всех `<img>` есть
`width`, `height`, `alt`» на странице без изображений выполняется тривиально:
spec выглядит работающим, не встретив ни одного тега. Поэтому страница
объявляет, что на ней должно быть, и обратное утверждение тоже проверяется —
`images: 'none'` означает «изображений нет», и появление изображения валит spec с
требованием объявить страницу заново.

Состояний по три там, где двух не хватило, и оба третьих появились из замеров, а
не из удобства:

| Поле | Состояния | Что означает третье |
|---|---|---|
| `images` | `none`, `primary`, `data-driven` | `data-driven` — состав изображений определяют ОПУБЛИКОВАННЫЕ записи (блок свежих открыток на главной). Утверждение есть в обеих ветвях: есть изображения — работает весь контракт `primary`; нет — на странице обязано не быть и плиток (`class="card-grid__item"`), потому что плитка без `<img>` означает потерянное изображение, а не пустую выборку. Прогон на пустой выборке помечается аннотацией «проверено нечем» |
| `structuredData` | `none`, `site`, `list` | `site` — документ описывает САЙТ (`WebSite`, при заполненном глобале `Organization`), и элементов списка в нём быть НЕ должно: крошек у главной нет по ТЗ §7.6, `ItemList` §5.2 от неё не требует. `list` — документ описывает видимый список (`BreadcrumbList`, `ItemList`), и каждый `ListItem` сверяется с видимым текстом и ссылками |
| `description` | `present`, `absent` | `absent` — тега нет вовсе. У информационных страниц — потому что текст берётся из глобала-заглушки (Ч-19) и правило «пустое поле — значит тега нет» (Ч-10, Ч-17) убирает тег целиком; у страниц пагинации — потому что `metaDescription` записи описывает первую страницу списка, а собирать описание шаблоном запрещено п. 23.4. Проверяется в обе стороны: появившийся description валит spec, а `absent` у ИНДЕКСИРУЕМОЙ страницы валит spec всегда (п. 22.1) |

Почему `structuredData: 'site'` — отдельное объявление, а не условие «`ListItem`
обязателен, когда в документе есть `WebPage`»: условие ослабляет проверку молча.
При нём страница, у которой разметка деградировала до одного `WebSite` (у
подборки пропали и крошки, и `ItemList`), проходила бы приёмку — узла `WebPage` в
документе уже нет, значит и списка не требуется. Объявление же говорит, чего от
страницы ЖДУТ, и любое расхождение — падение с требованием объявить страницу
заново.

## Как карточка, подборки, каталог и пагинация попали в инвентарь (Э4-07)

До задачи Э4-07 правило инвентаря звучало так: «сюда попадает только то, что
гарантирует КОД», то есть маршрут Astro со своим текстом. Оно отсекало карточку,
подборки, каталог и пагинацию — их страница существует только у ОПУБЛИКОВАННОЙ
записи, а записи в репозитории нет. Правило защищало от настоящей беды, и это не
теория: замерено 2026-08-27 в течение одного часа на одной машине — в 09:35
локальная база содержала следы смоука Э3-05, `/otkrytki` отвечал 200, на главной
было 12 плиток; в 10:05 записей уже не было, `/otkrytki` отвечал 404. Запись
каталога в инвентарь сделала бы `pnpm verify` красным у всех, у кого база пуста, и
зелёным у того, кто последним гонял смоук.

Расширение сохраняет ту же защиту и снимает цену, потому что различает два
утверждения, которые прежняя формулировка держала за одно:

1. **адрес** гарантирован репозиторием — пути подборок и slug'и открыток
   эталонной выборки Ч-06 лежат в `content/pilot-2026-08/site-content.json`,
   откуда каталог и импортируется. Приёмка адреса не выдумывает и не подбирает
   обходом сайта;
2. **существование** страницы по этому адресу — факт о базе, и зависеть от
   репозитория он не может: публикация есть решение человека (п. 7.1 и п. 23 ТЗ),
   а пустая подборка отвечает 404 намеренно (ТЗ §5.3).

Отсюда обещание приёмки, заменившее прежнее умолчание:

- страница, ОТДАЮЩАЯ 200, проверяется ПОЛНОСТЬЮ — тем же набором инвариантных
  specs, что и маршруты кода. Ни одного ослабленного утверждения для контентных
  страниц не заведено;
- страницу, которой нет, разбирает `declared-page-not-served.spec.ts`: он
  УТВЕРЖДАЕТ, что отсутствие выглядит ровно как 404 без `Location` (500 — дефект
  рендера, 3xx — редирект на каноническом адресе, 200 — страница есть и её надо
  проверять целиком), и ставит аннотацию «проверено нечем» с перечислением
  непроверенного и с условием появления страницы;
- `pnpm verify` на пустой базе остаётся зелёным, но ЧЕСТНЫМ: в выводе перечислено,
  чего он не проверил. Строку про состав печатает и `global-setup.ts` —
  сокращение выборки видно там же, где «388 passed», а не только в отчёте
  Playwright.

Три очевидные альтернативы отклонены, и разбор каждой — в шапке
`support/discovery.ts`; коротко:

1. **фикстуры (сеялка в приёмке).** `pnpm test:seo` входит в `pnpm verify`,
   который гоняет каждый агент на каждой задаче, — то есть стандартная команда
   проверки ПУБЛИКОВАЛА БЫ записи в базу контента, а оборванный прогон оставлял
   бы их опубликованными. Плюс: проверки на своих же фикстурах частью
   тавтологичны («title уникален» на данных, которые сеялка сама и написала,
   доказывает сеялку, а не сайт), а приёмка стала бы краснеть из-за PostgreSQL и
   пайплайна изображений — по причинам, к состоянию сайта не относящимся;
2. **подбор адресов обходом сайта.** Тогда ВЫБОРКА берётся из кода, который
   приёмка проверяет: сломанная сетка каталога давала бы не падение, а другую
   выборку;
3. **`test.skip` на отсутствующей странице.** Пропуск не показывает ни того, что
   не проверено, ни того, что нужно сделать, чтобы проверилось.

## Состав выборки сторожится тестом

`acceptance-sample-covers-checklist.spec.ts` проверяет не сайт, а саму приёмку: у
каждого из десяти видов страниц выборки п. 22 есть владелец — запись инвентаря с
таким `sampleRole` либо существующий spec-файл. Причина: сужение приёмки — самая
тихая из поломок. Удалить строку из инвентаря или файл spec'а можно, не сломав ни
одного теста: число тестов уменьшится, все останутся зелёными, и отчёт скажет
`PASSED`.

Тот же spec КАЖДЫЙ прогон печатает аннотацию «проверено нечем» про единственный
вид, у которого владельца в приёмке нет вовсе, — «удалённая карточка»: случаю
нужна запись в базе (снятая с публикации карточка плюс строка в `redirects`).
Названные вместо этого места (`tests/unit/web-redirects.test.ts`,
`apps/web/scripts/smoke-redirects.ts`, `apps/web/scripts/status-matrix-check.ts`)
проверяются на существование — ссылка на чужое покрытие обязана быть проверяемой,
иначе она однажды становится неправдой молча.

## Достижимость от главной (Э4-08)

`no-orphans.spec.ts` измеряет требование «нет страниц-сирот: каждая индексируемая
страница достижима за ≤ 4 перехода от главной» настоящим обходом серверного HTML
(`support/crawl.ts`), без JS и без браузера.

Список «обязанных быть достижимыми» собирается из трёх независимых источников:
карта сайта (в неё по построению входят только страницы 200 + self-canonical +
`index`), инвентарь приёмки (записи с директивой `index,…`) и живые ответы обхода
(страница фактически отдаёт `index,…`). Независимость нужна потому, что каждый
источник можно потерять по отдельности: пустая карта сайта может быть и признаком
своей поломки; обход же по определению не найдёт страницу, на которую нет ни
одной ссылки, — а именно она и есть сирота.

Правила подсчёта совпадают с обходом дашборда
(`apps/cms/src/audit/link-audit.ts`, Э5-03): ширина (минимальная глубина),
редирект переходом не считается, URL файлов не обходятся, предел числа запросов.
Расходятся два, и оба в безопасную сторону (могут добавить находку, но не
спрятать): адреса с параметрами в обход не берутся вовсе (индексируемой страницей
такой адрес не бывает — ТЗ §6.5, §5.5), и со страницы `nofollow` ссылки не
берутся (робот по ним не идёт). Код обхода СВОЙ, а не импорт из `apps/cms`, по
тому же доводу, что и копия набора robots-директив: правило подсчёта глубины —
это и есть эталон требования, и брать его из проверяемого кода нельзя.

Сам обход проверяется отдельным spec'ом — `crawl-depth-contract.spec.ts`, по той же
причине, по какой отдельно проверяется разборщик (см. раздел ниже): ошибка в
инструменте не делает тесты красными, она делает их неправдивыми. Здесь она
давала бы ЛОЖНУЮ находку «глубже нормы» на верной перелинковке, то есть красный
обязательный шлюз без причины. Spec поднимает свой крошечный сервер с ЗАДАННОЙ
топологией (цепочка редиректов приводит к адресу, уже найденному длинной
ссылкой) и требует, чтобы глубина потомков пересчиталась после понижения глубины
родителя. Замер 2026-09-03: при снятой правке spec падает с
`Expected: 3 / Received: 5` — ровно ложным «глубже нормы 4».

На 2026-09-03 индексируемых страниц ноль (в `index,follow` не открыта ни одна
страница сайта — решение человека, которого никто не принимал, Ч-04-1), поэтому
все три источника пусты и прогон помечается «проверено нечем». Чтобы пустая
аннотация не стала отпиской, в этом же состоянии УТВЕРЖДАЕТСЯ работоспособность
инструмента: главная обязана ответить 200, а обход — найти с неё больше одного
адреса; иначе сломанный обход выглядел бы точно так же, как честное «открытых
страниц пока нет». Замер того же прогона печатается строкой: обойдено адресов,
сделано запросов, максимальная измеренная глубина.


## Приёмка и инструменты CMS этапа 5: где они мешают друг другу

Этап 5 завёл в `apps/cms` механизмы, которые ходят на живой сайт по HTTP и живут
в той же базе, из которой читает стенд приёмки. Приёмка их не проверяет и
проверять не должна — это админка. Но соседство описать обязательно: один класс
помех (следы смоука в общей базе) уже стоил на этапе 3 семи ложных провалов.

| Инструмент | Куда ходит | Что пишет |
|---|---|---|
| выгрузка `GET /api/seo-inventory.csv` (Э5-05) | GET на origin из `SITE_URL`, `redirect: manual`, параллельность 6, предел 5000 строк | ничего |
| обход внутренних ссылок (Э5-03) | GET на origin из `SITE_URL`, параллельность 4, предел 2000 запросов | только глобал `link-audit-report` |
| дашборд SEO-здоровья (Э5-04) | никуда, читает базу правами смотрящего | ничего |
| смоуки `apps/cms/scripts/smoke-etap5-*.ts` | Local API | СОЗДАЮТ, ПУБЛИКУЮТ и удаляют записи контента |

**Выгрузка и обход приёмке не опасны.** В контентные коллекции они не пишут
(закреплено `apps/cms/src/audit/run.test.ts`), а глобал отчёта `apps/web` не
читает вовсе — на ответы сайта он не влияет. Остаётся только нагрузка: если
направить их на стенд приёмки, к серверу добавятся сотни запросов при бюджете
теста 45 с. Это даёт ЛОЖНЫЙ КРАСНЫЙ, а не ложный зелёный — направление
приемлемое, но совмещать незачем.

**Смоуки этапа 5 одновременно с приёмкой — опасны.**
`smoke-etap5-bulk-export.ts` создаёт записи, публикует их, на время ставит одной
`index,follow` и в `finally` удаляет всё. Пока это окно открыто, карта сайта НЕ
пуста, и specs, читающие её живьём, начинают проверять чужие адреса:
`sitemap-index-chain`, `sitemap-entries-are-indexable`, `sitemap-locs-are-clean`,
`sitemap-images-valid`, вторая половина `indexable-has-description`,
`filtered-view-not-indexable`. Каждый из них сначала читает карту, а потом
запрашивает каждый `<loc>` отдельным запросом: запись, удалённая между двумя
запросами, даёт 404 на адрес, только что названный картой, — то есть падение с
верным текстом и неверной причиной.

Инвентарь от этого защищён НЕ полностью, и после Э4-07 это надо читать точнее:
маршруты кода (`/`, `/search`, информационные) отвечают 200 при любом состоянии
базы, а шесть контентных страниц выборки — только пока записи опубликованы.
Запись, снятая с публикации ЧУЖИМ смоуком между замером присутствия
(`global-setup.ts`) и прогоном, даст падение с верным текстом и неверной
причиной: «страница инвентаря обязана отдавать 200». Карта сайта защищена быть не
может вовсе — её состав и есть содержимое базы.

**Правило: `pnpm test:seo` и смоуки `apps/cms` не гоняются одновременно на одной
базе.** Замера «сколько длится окно» здесь нет намеренно: оно зависит от того,
где смоук сейчас находится, и ловится не всегда — а помеха, срабатывающая через
раз, хуже постоянной.

**Публичного хоста инструменты этапа 5 не получили.** Замерено 2026-08-29 на
собранном сервере `apps/web`: `/api/seo-inventory.csv` и `/api/cards` отвечают
404 без `Location`, `robots.txt` содержит прежние три `Disallow` и ни одной
строки про `/api`, индекс карты сайта пуст. Ручку обслуживает `apps/cms` на своём
порту, и анониму она отвечает 403. Отдельного spec на это не заведено — сегодня
ему нечего утверждать; строка добавлена в таблицу ниже.

## Разборщик приёмки проверяется отдельно

`html-parser-contract.spec.ts` проверяет не сайт, а `support/html.ts` — то, ЧЕМ
приёмка видит ответ сервера. Ошибка в разборщике не делает тесты красными, она
делает их неправдивыми: часть проверок начинает утверждать не то, что написано в
их сообщениях. Оба случая в этом spec'е реальны:

- **пустое значение атрибута Astro печатает бескавычно.** `alt=""` приезжает как
  `<img … alt>` (`addAttribute` в `astro/dist/runtime/server/render/util.js`,
  astro 7.2.4). Прежний разбор такой атрибут не находил вовсе, поэтому
  декоративное изображение с законным пустым `alt` выглядело бы как изображение,
  у которого `alt` забыли, — приёмка обвинила бы владельца слоя в нарушении,
  которого нет. Сейчас различаются три состояния: атрибута нет (`null`), атрибут
  есть и пуст (`''`), атрибут есть со значением;
- **`\b` перед именем ловил чужой атрибут.** `data-src` отвечал за `src`. Это
  обратная и более опасная ошибка: изображение, подставляемое скриптом из
  `data-src` (ровно то, что запрещает раздел «Рендеринг»), выглядело бы как
  изображение с настоящим `src`.

Серверу этот spec не нужен: он о разборе строк. Падение в нём говорит о приёмке,
а не о состоянии сайта.

### XML разбирается браузером, а не регулярным выражением

`support/xml.ts` разбирает файлы карты сайта через `DOMParser` в контексте
chromium — того же браузера, которым приёмка проверяет видимость контента без JS.
Причина в шапке модуля, коротко: у HTML и XML разная цена ошибки разбора. HTML
браузер чинит, поэтому в `support/html.ts` разбор намеренно узкий; XML не чинит
никто — поисковая система отвергает дефектный файл карты целиком. Регулярное
выражение достало бы `<loc>` и из документа с оборванным `</urlset>`, то есть
spec остался бы зелёным на файле, который Яндекс и Google не примут. Свой парсер
well-formedness писать здесь нельзя по той же логике, по какой приёмка не берёт
эталон из проверяемого кода: «валидный XML» означало бы «прошёл мой парсер».
Проверено экспериментом 2026-08-28: при удалении `</sitemapindex>` из ответа spec
падает с сообщением парсера «Premature end of data in tag sitemapindex line 2».

### Набор значений robots у приёмки — свой

Внутри продукта набор один: с задач Э4-05 и Э4-06 он живёт в `@otkritka/shared`,
и своих копий нет ни у `apps/cms`, ни у `apps/web`.
`ALLOWED_ROBOTS_DIRECTIVES` в `support/declared-pages.ts` дублирует его НАМЕРЕННО. Разбор — в комментарии к константе; коротко:
приёмка не берёт эталон из кода, который проверяет. При импорте общего набора
новое значение директивы, добавленное в `packages/shared`, приёмка приняла бы
автоматически и молча — а директива управляет попаданием страницы в индекс.
Копия же самосторожащая: расширение набора в коде валит приёмку с «значение не
входит в список допустимых директив проекта», сужение оставляет приёмку строже
кода. Тождество наборов ВНУТРИ продукта проверяет `tests/unit/robots.test.ts` —
там ему и место.

## Чего приёмка пока НЕ проверяет

Список ведётся здесь, чтобы зелёный прогон не читался как «чек-лист п. 22 закрыт».
Каждая строка снимается вместе с задачей, которая создаёт проверяемое.

Общая причина у большинства строк одна: **проверяемое существует только у
опубликованной записи**. С задачи Э4-07 часть таких строк снята: страница, чей
адрес гарантирован репозиторием, входит в выборку и проверяется целиком там, где
отдаётся (разбор выше). Осталось непокрытым то, чего нет ни в одной базе
(снятая с публикации карточка, редиректы) и то, что зависит от РЕШЕНИЯ ЧЕЛОВЕКА
об открытии в индекс.

Отдельно от «не покрыто» отмечается **пустой прогон**: spec написан, зелёный, но
проверять ему пока нечего. Такой прогон помечается аннотацией «проверено нечем»
прямо в отчёте Playwright и попадает в таблицу ниже — зелёный статус на пустом
множестве покрытием не является.

| Требование п. 22 | Почему не покрыто | Снимется на |
|---|---|---|
| sitemap: **состав** — только 200 + canonical + indexable | ПУСТОЙ ПРОГОН. `sitemap-entries-are-indexable`, `sitemap-locs-are-clean`, `sitemap-images-valid` и вторая половина `indexable-has-description` обходят индекс и проверяют каждый адрес. В индексе ноль файлов: ни одна страница не открыта в `index,follow` (Ч-04-1). Правок в specs не потребуется — состав они берут из самого индекса | первая страница с `index,follow` |
| sitemap: image sitemap валиден | ПУСТОЙ ПРОГОН по той же причине: файла `sitemap-images-N.xml` не существует, пока нет открытых карточек | первая карточка с `index,follow` |
| перенос — одиночный 301 на конечный адрес; удалено без замены — 410; удалено с заменой — 301 НЕ на главную; удалённая карточка не отдаёт 200 с параметрами | правило реализовано (Э4-02) и покрыто юнит-тестом `tests/unit/web-redirects.test.ts` на каждый случай, включая цепочку и петлю. Для этого нужна подборка, где страниц списка больше одной, то есть больше 24 опубликованных открыток в одной теме; у каталога `/otkrytki` ряда фильтра нет вовсе. Адрес `/otkrytki/prazdniki/8-marta/page/2` объявлен в инвентаре и сейчас отвечает 404 — утверждение сработает само, без правок | публикация 25+ открыток в одной теме |
| нет страниц-сирот: ≤ 4 перехода от главной | ПУСТОЙ ПРОГОН. | каждая открытая в индекс страница ПОПАЛА в карту сайта | обратное направление («в карте только 200 + canonical + indexable») проверяет `sitemap-entries-are-indexable.spec.ts`. Частично его уже держит `no-orphans.spec.ts`: страница, отдающая `index,…` и не попавшая в карту, всё равно входит в множество «обязанных быть достижимыми» из живого ответа | первая страница с `index,follow` |
| проверяемая машиной часть условий п. 5.1 | ни одной индексируемой страницы нет — блок specs существует, но тестов не порождает | первая страница с `index,follow` |

| `X-Robots-Tag: noindex` и Basic Auth на staging (Ч-18) | стенда нет, адрес назначается на этапе 7 | Э7-01 |
| `Cache-Control` у файлов шрифтов — **не п. 22, а раздел «Производительность»** | замерено 2026-08-31: `apps/web` отдаёт файлы из `public/` без заголовка кеширования вовсе. Утверждение здесь зафиксировало бы конфигурацию dev-стенда приёмки как норму, тогда как «длительное кеширование статики» — свойство развёртывания (обратный прокси; по `/media` требование задано решением Ч-03). Существование и тип самих файлов покрыты: `preloaded-fonts-are-served.spec.ts` | Э7-01 |

## Найденное нарушение, переданное владельцу слоя

Приёмка нарушений не исправляет — называет. На прогоне 2026-09-03 (первый прогон
расширенной выборки) `not-found-body-is-single.spec.ts` упал: тело 404 у ветвей
`/media/<нет файла>` и `<путь админки>` оказалось резервным (270 байт) при том,
что промах маршрута отдавал настоящую страницу (17 569 байт). Причина найдена
чтением кода и воспроизведена вручную — `apps/web/src/server/front-door.ts`:

```ts
let notFoundBody: Buffer | string | undefined;

async function loadNotFoundBody(clientRoot: string): Promise<Buffer | string> {
  if (notFoundBody !== undefined) return notFoundBody;
  try {
    notFoundBody = await readFile(path.join(clientRoot, NOT_FOUND_PAGE_FILE));
  } catch {
    notFoundBody = FALLBACK_NOT_FOUND_HTML;
  }
  return notFoundBody;
}
```

ОДНА неудача чтения `dist/client/404.html` — временная (EMFILE при параллельной
нагрузке, конкуренция за файл во время пересборки) — кешируется НАВСЕГДА: до
перезапуска процесса каждый 404 входного обработчика отдаёт резервные 270 байт
вместо страницы с навигацией (требование ТЗ §5.6). Ни повторной попытки, ни
записи в журнал: `catch {}` глотает ошибку, хотя `logError` в опциях есть и
рядом используется. Второй прогон в тот же день прошёл целиком (388 passed) —
то есть дефект нагрузочно-зависимый, и без этого падения о нём никто бы не узнал.

Владелец — `astro-web`. Повторов в конфиге приёмки нет намеренно: повтор здесь
не лечил бы флак, а прятал бы настоящую нестабильность ответа сервера.

## Поле `expectedRobots` в инвентаре

Оно фиксирует, что страница отдаёт сейчас, и охраняет границу: перевод страницы в
`index,follow` — решение человека (п. 7.1 и п. 23 ТЗ). Молчаливое открытие
индексации после правки layout иначе не поймать — в браузере оно выглядит как
раньше. Когда человек открывает страницу осознанно, правка этой строки входит в
его решение и видна в дифе. Аудитор значение не «повышает» сам.

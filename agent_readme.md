# agent_readme.md — работа с агентами в проекте открыток

Инструкция по мультиагентской разработке этого репозитория: кто за что отвечает,
как ставить задачу, и — главное — **что обязательно сделать по окончании работы**,
прежде чем сказать «готово».

Готовые промпты запуска, матрица параллельности и чек-лист приёмки работы агента —
в `docs/agents-launch.md`. Здесь — процесс и границы, там — что именно копировать
в вызов.

Источники истины, в порядке приоритета при противоречиях:

1. `docs/seo-requirements.md` — полное SEO ТЗ;
2. `CLAUDE.md` — постоянный контекст проекта;
3. этот файл — процесс и границы агентов.

Этот файл описывает **процесс**, а не требования. Если здесь и в ТЗ написано
разное о содержании работы — прав ТЗ.

## Почему обвязка устроена именно так

Органический трафик из Яндекса и Google — главный канал проекта, поэтому
SEO-требования приоритетнее скорости разработки. Из этого следуют две
конструктивные особенности, которые нельзя «оптимизировать»:

- **Контролёры с правом вето.** Зелёный `pnpm verify` не означает, что задача
  выполнена: часть требований (URL, canonical, редиректы, условия индексации)
  проверяется отдельными агентами, и их FAIL блокирует завершение.
- **Жёсткая граница автоматизации.** Агенты доводят контент до статуса `review`.
  Публикация и открытие в `index,follow` — осознанное действие человека, всегда.
  Это требование ТЗ (п. 7.1, п. 23), а не перестраховка.

## Состав команды агентов

Определения — в `.claude/agents/`. Вызов — через Agent tool по имени.

### Реализаторы (пишут код, каждый в своей папке)

| Агент | Владеет | Отвечает за |
|---|---|---|
| `astro-web` | `apps/web/` | роуты, шаблоны, хлебные крошки, пагинация, sitemap, robots, middleware редиректов, JSON-LD, вывод изображений |
| `payload-cms` | `apps/cms/` | коллекции, хуки `beforeChange`, access control, роли `admin`/`ai-editor`, `seo-history` |
| `images-pipeline` | `packages/images/` | sharp, AVIF/WebP/JPEG, наборы размеров, pHash, имена файлов |
| `shared-core` | `packages/shared/` | транслитерация в slug, валидация URL, `TRAILING_SLASH`, типы статусной модели |

За пределами своей папки реализатор только читает. Нужна правка в чужой зоне —
задача передаётся владельцу, а не делается «по-быстрому».

`packages/shared/` — общий контракт, от которого зависят и `web`, и `cms`. Поэтому
у него есть выделенный владелец: добавление экспорта — обычная правка, изменение
или удаление существующего — ломающее, требует списка потребителей в отчёте и
согласования с владельцами слоёв. Правка, которая может задеть уже существующие
URL, идёт через вердикт `url-guard`.

### Редактор контента (пишет текст, не код)

| Агент | Владеет | Отвечает за |
|---|---|---|
| `content-editor` | содержание записей, `docs/content/` | title, H1, description, вводный текст, alt, подписи, привязка карточек к подборкам, перелинковка, `draft` → `review` |

Работает в роли `ai-editor`: границы те же, что у внешнего AI-редактора через API,
и подтверждены access control, а не только инструкцией.

### Контролёры (только читают, имеют право вето)

| Агент | Проверяет | Когда обязателен |
|---|---|---|
| `url-guard` | правила URL, canonical, одиночные 301, отсутствие цепочек, состав sitemap | тронуты slug, роут, canonical, редиректы, sitemap |
| `seo-auditor` | чек-лист приёмки п. 22, условия индексации п. 5.1, владеет `tests/seo/` | тронуты шаблон, роутинг, sitemap, коллекции, изображения |
| `perf-guard` | LCP/INP/CLS/TTFB, вес HTML, резервирование места под изображения и рекламу, порядок загрузки CSS/JS | тронуты шаблоны, вывод изображений, скрипты рекламы, конфиг сборки |
| `reviewer` | запреты п. 23 и соглашения по коду | всегда, для любого дифа |

Контролёр называет нарушение и не исправляет его. Исправляет владелец слоя,
после чего проверки прогоняются заново.

### Координатор

| Агент | Роль |
|---|---|
| `planner` | декомпозиция задачи на назначения, порядок, точки вето, список решений для человека. Кода не пишет |

## Как выбрать агента

| Задача | Вызов |
|---|---|
| Правка в одном слое, владелец очевиден | сразу нужного реализатора |
| Затронуто два слоя и больше | `planner`, затем реализаторов по его плану |
| Правка общего контракта в `packages/shared` | `shared-core`, затем потребители |
| Текст, метаданные, alt, перелинковка | `content-editor` |
| «Где определён X», «что вызывает Y» | `Explore` (обычный поиск, не нужен профильный агент) |
| Проверить готовую работу | `reviewer` + профильные контролёры |
| Непонятно, что требует ТЗ | `planner`; если ТЗ молчит — вопрос человеку, а не догадка |

Мелкая механическая правка в одном файле не требует агента вообще: делайте её
напрямую и переходите к протоколу завершения.

## Запуск агентов

Независимые задачи запускаются одним сообщением с несколькими вызовами Agent tool
— тогда они идут параллельно. Правило параллельности: **разные папки — можно
одновременно, одна папка — нельзя**.

```text
Одним сообщением (независимы):
  payload-cms      -> apps/cms/src/collections/cards.ts
  images-pipeline  -> packages/images/src/phash.ts

Последовательно (есть зависимость по типам):
  payload-cms (коллекция + generate:types)  ->  astro-web (шаблон по типам)
```

Если два реализатора обязаны править один пакет — запускайте их с
`isolation: "worktree"`, чтобы правки не конфликтовали. Контролёрам worktree не
давайте: им нужен реальный рабочий каталог с текущим дифом.

Постановка задачи агенту всегда включает: цель, границы (какие файлы можно),
контекст (какие документы читать), критерий готовности, точки вето и напоминание
про протокол завершения. Агент не видит историю вашего диалога — контекст
передаётся в промпте.

Готовые промпты по каждому агенту, которые остаётся только подставить под задачу,
лежат в `docs/agents-launch.md` (раздел «Готовые промпты»).

## Что агент не может делать никогда

Эти запреты действуют для всех агентов и для внешнего AI-редактора через API
Payload. Они реализованы в серверных хуках и access control, а не только в
инструкциях, — поэтому обойти их через API нельзя.

- Переводить контент в `published`.
- Переключать `index/noindex`, открывать страницу в `index,follow`.
- Менять slug после первой публикации.
- Создавать и менять редиректы (роль `ai-editor`).
- Трогать robots-директивы и sitemap вручную (роль `ai-editor`).
- Массово создавать URL до готовности контента.
- Публиковать результат нейросетевой генерации без ручной модерации.

Что агент может: создавать и править записи в `draft`, загружать изображения,
заполнять метаданные и alt, привязывать карточки к подборкам, расставлять
внутренние ссылки, переводить `draft` → `review`.

Каждый шаг агента прослеживаем: `seo-history` фиксирует автора любого изменения
SEO-полей, включая сервисный аккаунт.

## По окончании работы — обязательный протокол

Полная версия и шаблон отчёта — в skill `finish-task` (`.claude/skills/finish-task/`).
Skill вызывается автоматически, когда агент собирается заявить о готовности; здесь
— та же последовательность для человека-оператора.

### Шаг 1. `pnpm verify` целиком

```bash
pnpm verify
```

Зелёный целиком. Вывод сохраняется и попадает в отчёт. Красный verify означает,
что задача не выполнена, — независимо от размера правки.

### Шаг 2. SEO-замер до и после

Обязателен, если тронуты шаблон страницы, роутинг, sitemap, robots, коллекции
Payload или вывод изображений:

```bash
pnpm test:seo   # до правки
pnpm test:seo   # после правки, дельта в отчёт
```

Шлюз `scripts/seo-gate.mjs` печатает один из трёх статусов:

| Статус | Значение |
|---|---|
| `SEO_ACCEPTANCE: PASSED` | прогнано против `BASE_URL`, всё зелёное |
| `SEO_ACCEPTANCE: FAILED` | нарушено конкретное требование, задачу закрывать нельзя |
| `SEO_ACCEPTANCE: SKIPPED` | **не проверено** (нет spec-файлов или не задан `BASE_URL`) |

`SKIPPED` — не прохождение. Он существует только для того, чтобы `verify` был
зелёным на скелете, пока сайт не поднят. Статус переносится в отчёт дословно,
вместе с причиной. Выдача `SKIPPED` за `PASSED` — самая дорогая ошибка
отчётности в этом проекте: она снимает страховку с приоритетного требования.

### Шаг 3. Вердикты контролёров

| Что тронуто | Кого вызвать |
|---|---|
| slug, роут, canonical, редиректы, sitemap, правила URL в `shared` | `url-guard` |
| шаблон, роутинг, sitemap, коллекции, изображения | `seo-auditor` |
| шаблоны, вывод изображений, скрипты рекламы, конфиг сборки | `perf-guard` |
| любой диф | `reviewer` |

FAIL блокирует завершение даже при зелёном `verify`. Находки идут владельцу
слоя, после исправления шаги 1–3 повторяются.

`seo-auditor` и `perf-guard` имеют право на вердикт `НЕ ПРОВЕРЕНО` — когда сайт
ещё не поднят. Это законный результат; подменять его на `PASS` запрещено.

### Шаг 4. Отчёт

Фиксированный шаблон (полностью — в skill `finish-task`), с обязательными
разделами:

```markdown
## Что сделано
## Файлы
## Проверка          — verify, test:seo до/после, вердикты контролёров
## Статусы контента  — что в draft, что в review, published всегда «нет»
## Требует решения человека
## Не сделано
```

Пустые разделы не удаляются: «нет» — это информация, отсутствие раздела —
неизвестность. Раздел «Требует решения человека» — не формальность: там
перечисляются кандидаты на публикацию, спорные места ТЗ и всё, что упирается в
границу автоматизации.

### Шаг 5. Коммит

Малый, оставляет проект в состоянии зелёного `pnpm verify`. Сообщение — обычным
языком.

### Передача между агентами

Отчёт предыдущего агента — вход для следующего. Передавайте его целиком:
разделы «Проверка» и «Не сделано» избавляют следующего агента от повторного
прогона тех же проверок и от догадок о том, где остановился предыдущий.

## Автоматические напоминания

`.claude/settings.json` подключает два хука. Оба только напоминают и ничего не
блокируют — блокирует протокол, а не автоматика.

| Хук | Когда | Что делает |
|---|---|---|
| `seo-touch-reminder.mjs` | после `Write`/`Edit` | если файл в зоне SEO-риска (шаблоны, middleware, sitemap/robots, коллекции, `packages/shared`, пайплайн изображений, рекламные блоки) — напоминает про `test:seo` и называет контролёров, обязательных именно для этой зоны |
| `finish-reminder.mjs` | при остановке | печатает чек-лист протокола завершения |

## Команды

```bash
pnpm install                # первая установка
pnpm verify                 # check + test + test:seo — перед завершением ЛЮБОЙ задачи
pnpm check                  # tsc -b + eslint
pnpm test                   # Vitest
pnpm test -t "имя теста"     # один тест
pnpm exec vitest run tests/unit/workspace.test.ts   # один файл
pnpm test:seo               # приёмка SEO через шлюз
BASE_URL=http://localhost:4321 pnpm test:seo        # приёмка против поднятого сайта
pnpm generate:types         # типы Payload из коллекций (после apps/cms)
pnpm dev                    # dev-серверы web + cms (после установки приложений)
```

## Состояние скелета и известные пробелы

Скелет монорепозитория собран и `pnpm verify` на нём зелёный
(`check` — проходит, `test` — 3 теста, `test:seo` — `SKIPPED`, сайта пока нет).

Что ещё не сделано и кто это делает:

| Пробел | Владелец | Примечание |
|---|---|---|
| `docs/seo-requirements.md` — только каркас | человек | CLAUDE.md называет файл источником истины; содержание ТЗ агентами не выдумывается |
| Astro не установлен в `apps/web` | `astro-web` | ставится в гибридном режиме вместе с первым роутом |
| Payload и PostgreSQL не установлены в `apps/cms` | `payload-cms` | требует доступа к БД |
| sharp не установлен | `images-pipeline` | ставится с первой реализацией |
| Playwright и spec-файлы в `tests/seo/` отсутствуют | `seo-auditor` | до их появления `test:seo` даёт `SKIPPED` |
| Утилиты `packages/shared`: транслитерация, валидация URL | `shared-core` | до их появления правила URL живут только в документации, а не в исполняемом виде |
| MCP-обёртка над Payload API для внешнего AI-редактора | `payload-cms` | тонкая обёртка операциями уровня задач; бизнес-правила остаются в хуках Payload и не дублируются в обёртке |
| Контентные черновики в `docs/content/` | `content-editor` | вход для переноса в CMS, пока Payload не поднят |

`pnpm dev`, `pnpm build` и `pnpm generate:types` пока выходят с ошибкой и явно
сообщают причину — это заглушки скелета, а не сломанная сборка. Так сделано
намеренно: команда, которая «есть, но ничего не делает», однажды будет принята за
успешную.
